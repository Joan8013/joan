# 需求澄清 v2

需求：REQ-003 ETC拓展平台结算服务费开票功能

本文基于原始需求重新整理，本版按以下前提收敛范围：

1. 不处理前置审核流程。
2. 不处理发票拆分规则，拆分结果由前一流程负责产出。
3. 本期只做发票开票和发票记录管理。
4. 开票金额来源统一追溯到服务费汇总表中的服务费汇总记录。
5. 本流程只接收前一流程已经确认好的开票字段信息，不在本流程重新决定拆票、发票类型等内容。

## 1. 需求目标

在 ETC 拓展平台中补齐“服务费发票开具 + 发票记录管理”能力，实现：

1. 针对服务费汇总记录发起开票。
2. 记录每次开票结果和票面信息。
3. 为商户提供统一的发票记录查询页面。
4. 对失败记录提供重试操作。
5. 对成功记录提供发票下载操作。

本需求目标不是搭建完整的申请、审核、拆票、红冲闭环，而是先把最小可用的开票和结果管理能力落地。

## 2. 本期范围

本期纳入范围的功能如下：

1. 以前一流程产出的待开票数据作为本流程开票输入。
2. 待开票数据中需包含开票所需完整字段信息，如服务费汇总记录编码、发票类型、开票金额、购销方信息及其他接口必填项。
3. 系统基于前一流程传入的开票字段信息发起乐企开票。
4. 开票成功后保存发票号码、发票代码、开票时间、下载地址等信息。
5. 开票失败后保存失败状态和失败原因。
6. 提供前端页面，按商户展示已开过的发票记录。
7. 每条发票记录提供可操作能力：
8. 开票失败时可执行“重试”。
9. 开票成功时可执行“下载发票”。

## 3. 本期非范围

以下内容明确不纳入本期：

1. 开票前审核流程。
2. 发票拆分、多张发票分摊同一笔金额。
3. 红冲、作废、换票、重开发票后的逆向财务处理。
4. 商户在线修改购买方抬头、税号等开票主体信息。
5. 发票申请单、审核单等独立流程单据。
6. 本流程不提供对开票报文中的项目明细 `COMMON_FPKJ_XMXX` 进行手工编辑的能力，项目明细数据由前一流程生成并完整传入。
7. 对服务费汇总口径本身的计算逻辑改造。
8. 在本流程内重新决定发票类型、拆票结果、申请信息。

## 4. 业务对象澄清

### 4.1 主业务对象

本需求主对象统一定义为：`待开票记录`。

说明：

1. 待开票记录由前一流程产出。
2. 待开票记录中必须带出服务费汇总记录编码。
3. 服务费汇总记录来自服务费汇总表，是金额来源追溯对象，不是本流程内直接拆票的操作对象。
4. 一个服务费汇总记录最终可能对应多张发票，但这种拆分关系由前一流程决定，本流程只消费拆分后的待开票记录。

### 4.2 开票对象关系

当前按如下规则理解：

1. 一条待开票记录对应一次开票请求。
2. 一次开票请求对应一张发票。
3. 一张发票必须能追溯到来源服务费汇总记录编码。
4. 若首次开票失败，后续“重试”仍针对同一条待开票记录进行。
5. 一条服务费汇总记录可对应几张发票，不在本流程内判断，只承接前一流程结果。

### 4.3 接口关键标识

本流程需要区分以下两个接口字段：

1. `FPQQLSH`：发票请求流水号，20 位，企业内部唯一，一个流水号只能对应一次开票请求，是乐企侧识别同一笔开票请求的幂等键。
2. `LSH`：异步流水号，36 位，供异步返回或异步推送时使用，用于轮询或回调场景下识别异步处理结果。

当前约束：

1. 失败重试时必须复用原 `FPQQLSH`。
2. `LSH` 不等同于 `FPQQLSH`，不能用来替代开票请求幂等键。
3. 若本期不接入异步回调，`LSH` 可按接口需要决定是否传入，但不影响 `FPQQLSH` 作为主幂等键的地位。

## 5. 核心业务规则

### 5.1 金额来源规则

1. 开票金额不得手工录入。
2. 开票金额由前一流程传入，但金额来源需可追溯到服务费汇总表中的服务费汇总记录。
3. 本流程不负责判断一条服务费汇总记录是否被拆成多张发票。
4. 金额字段口径需遵循乐企接口约束。
5. 根据接口材料当前可引用的明确口径，金额类字段按“单位元，两位小数”理解。
6. 拆票场景下的金额精度和尾差处理规则，由前一流程在生成待开票记录时确定。
7. 本流程接收的每张待开票记录中的 `JSHJ`、`HJJE`、`HJSE` 均视为已可直接开票的最终金额，不做二次计算和修正。

### 5.2 开票结果规则

1. 开票成功后，系统保存开票成功结果。
2. 开票失败后，系统保存失败原因，供页面展示和后续重试使用。
3. 开票成功的记录支持下载发票。
4. 开票失败的记录支持重试。

### 5.3 失败重试规则

1. 本需求统一使用“重试”术语，不使用“重开”描述失败后的再次提交动作。
2. “重试”是指对同一条待开票记录、同一 `FPQQLSH`、同一开票报文进行原样重新提交。
3. 重试仅针对状态为“开票失败”的记录开放。
4. 重试时不允许重新生成新的 `FPQQLSH`。
5. 重试时不允许修改金额来源、发票类型、项目明细及其他前序已确定的开票字段。
6. 最大重试次数限制为 3 次。
7. 每一笔开票请求需对应一个唯一的 20 位字母和数字组合的 `FPQQLSH`。
8. `FPQQLSH` 长度固定为 20 位，需由系统按固定规则生成并保证全局唯一。
9. 如请求失败，特别是 `9992`、`9999` 或请求超时场景，必须使用之前完全一致的开票报文再次申请，否则可能造成重复开票。
10. 业务口语中的“作废后重新开一张新票”不属于本期“重试”范围。

## 6. 页面需求

本期需要提供“发票记录管理页面”，用于展示商户已开过的发票记录。

### 6.1 页面定位

页面目标：

1. 让商户查看自己已发起过的服务费发票记录。
2. 让商户快速识别成功和失败记录。
3. 让商户对失败记录执行重试。
4. 让商户对成功记录执行发票下载。

### 6.2 页面展示字段

建议至少展示以下字段：

| 字段 | 说明 |
| --- | --- |
| 待开票记录号 | 前一流程产出的待开票主键 |
| `FPQQLSH` | 本次开票请求唯一标识 |
| 服务费汇总记录编码 | 发票来源业务编码 |
| 商户名称 | 发票所属商户 |
| 业务类型 | 结算服务费 |
| 开票金额 | 来自前一流程确认后的开票金额 |
| 发票类型 | 前一流程申请时已确定的普票/专票 |
| 发票号码 | 开票成功后展示 |
| 发票代码 | 开票成功后展示 |
| 开票时间 | 开票成功时间 |
| 开票状态 | 待开票/开票中/开票成功/开票失败 |
| 失败原因 | 开票失败时展示 |
| 操作 | 重试 / 下载 |

说明：

1. 发票类型由前一流程申请时确定，本页面只做展示，不提供修改能力。
2. 页面核心必须同时支持“`FPQQLSH`”和“服务费汇总记录编码”两层追踪。

### 6.3 页面操作规则

1. 当发票状态为“开票失败”时，操作项展示“重试”。
2. 当发票状态为“开票成功”时，操作项展示“下载发票”。
3. 其他状态下不展示无效操作，或置灰展示，交互方式由产品确定。
4. “下载发票”默认优先使用 `PDF_URL` 下载 PDF 文件。
5. 若 `PDF_URL` 为空，可降级使用 `OFD_URL`。
6. `XML_URL` 是否对用户开放下载，由产品在方案阶段最终确认。

## 7. 状态口径

结合当前范围收敛，本期建议最少保留以下状态：

| 状态 | 含义 |
| --- | --- |
| 待开票 | 待开票记录已生成，但尚未调用 `GP_FPKJ` 接口 |
| 开票中 | 已调用 `GP_FPKJ`，接口返回异步处理中，尚未拿到最终结果 |
| 开票成功 | `GP_FPKJ` 返回成功，且票面和下载地址信息可用 |
| 开票失败 | `GP_FPKJ` 返回失败，记录失败原因，可执行重试 |

说明：

1. 本版不引入审核相关状态。
2. `待开票` 属于纯业务状态，不直接对应乐企接口返回码。
3. `开票中` 对应接口返回 `CODE=1000` 或尚未收到异步最终结果的场景。
4. `开票成功` 对应接口返回 `CODE=0000`，且 `FP_DM`、`FP_HM`、`PDF_URL` 等关键字段已回写。
5. `开票失败` 对应接口返回 `CODE != 0000` 且 `CODE != 1000` 的场景。

## 8. 权限范围

当前建议按以下规则理解：

1. 商户只能查看自己名下的发票记录。
2. 商户只能对自己名下失败记录执行重试。
3. 商户只能对自己名下成功记录执行下载。
4. 平台侧如需查看全部记录，可在后续设计中补充后台查询能力，但不作为本次用户前台页面核心目标。
5. 可开票范围限定为未开过票的服务费汇总记录对应的待开票数据。

## 10. 澄清结论

1. 本需求本期只聚焦“开票执行”和“发票记录管理”，不延伸到审核和拆票。
2. 本流程的输入不是原始服务费汇总记录本身，而是前一流程已经整理完成的待开票字段数据。
3. 发票金额来源需可追溯到服务费汇总表中的服务费汇总记录，发票类型也以前一流程申请结果为准。
4. 页面核心是按商户展示历史开票记录，并基于结果状态提供“失败重试、成功下载”两类操作。
5. `FPQQLSH` 是关键幂等标识，方案设计时必须保证失败重试沿用原 `FPQQLSH` 和原报文，避免重复开票。
6. `LSH` 仅用于异步返回或推送场景，不能替代 `FPQQLSH` 的开票请求幂等职责。
