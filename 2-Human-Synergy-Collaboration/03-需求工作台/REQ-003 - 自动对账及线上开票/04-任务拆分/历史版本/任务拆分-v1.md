# 任务拆分 v1

需求：`REQ-003 ETC拓展平台结算服务费开票功能`

本文基于以下文档拆分任务：

1. `01-需求澄清/需求澄清-v2.md`
2. `02-影响分析/影响分析-v1.md`
3. `03-方案设计/方案设计-v2.md`
4. `03-方案设计/发票表设计-v2.md`

本文目标是把当前方案拆成可执行、可排期、可验收的开发任务。

## 1. 任务拆分原则

1. 本期只覆盖开票执行、发票记录管理、失败重试、成功下载。
2. 不拆审核流、不拆拆票流、不拆红冲作废流。
3. 任务颗粒度以“一个开发同学可以独立交付并联调”为准。
4. 每个任务都要有明确交付物和验收方式。
5. 本期开发采用 TDD，后端核心逻辑和前端关键交互均按“先写测试，再写实现，最后回归”的顺序推进。

## 1.1 TDD 执行要求

本期不是“开发完再补测试”，而是把测试作为开发任务的一部分同步推进。

执行要求：

1. 后端核心 Service、状态流转、重试幂等、权限校验必须先补测试用例，再写实现。
2. 前端列表展示、操作按钮显隐、重试交互、下载交互应补组件或页面行为测试。
3. 每个 P0 任务完成时，必须同时交付对应测试，而不是把测试堆到最后。
4. `06-测试与验收` 阶段负责的是回归测试、完成前验证和验收结论，不替代开发期 TDD；联调过程记录在 `05-开发与联调`。

## 3. 详细任务拆分

## 3.1 数据库任务

### TASK-001 冻结发票主表与重试日志表DDL

目标：

1. 在数据库中落地 `etcplus_service_fee_invoice`
2. 在数据库中落地 `etcplus_service_fee_invoice_retry_log`

交付物：

1. 建表 SQL
2. 索引和唯一约束
3. 字段注释

验收标准：

1. 主表字段与 `发票表设计-v2.md` 一致
2. `fpqqlsh` 唯一约束存在
3. 不包含审核、拆票、逻辑删除等非本期字段

备注：

1. 若生产库不是 MySQL 8.0，字符集按实际库规范执行，但不得回退到 `utf8mb4_0900_ai_ci`

## 3.2 后端任务

### TASK-001A 补齐后端 TDD 测试骨架与用例清单

目标：

1. 在实现前先冻结后端测试边界
2. 为核心 Service 和接口准备测试骨架

交付物：

1. 后端测试类清单
2. 核心测试场景清单
3. Mock 方案或测试数据准备方案

至少覆盖：

1. 创建记录并生成 20 位 `fpqqlsh`
2. `CODE=0000` 成功回写
3. `CODE=1000` 开票中回写
4. 同步失败回写
5. 失败状态才允许重试
6. 重试必须复用原 `fpqqlsh` 和原报文
7. 超过 3 次禁止重试
8. 商户越权访问校验

验收标准：

1. 测试类和测试方法命名可直接映射到 P0 任务
2. 测试场景覆盖状态机、幂等、权限三类高风险逻辑
3. 先有测试清单，再开始核心实现开发

### TASK-002 实现服务费发票主表与日志表后端对象

目标：

1. 新增 `ServiceFeeInvoice`
2. 新增 `ServiceFeeInvoiceRetryLog`
3. 新增对应 Mapper 和 XML

交付物：

1. Domain 类
2. Mapper 接口
3. Mapper XML

验收标准：

1. 主表与日志表字段映射完整
2. 查询和插入能力可用
3. 字段名与数据库正式模型一致

### TASK-003 实现服务费开票入口接口

目标：

1. 提供供前一流程调用的“创建并发起开票”接口
2. 入参只接收已冻结的待开票字段

建议接口：

1. `POST /system/serviceFeeInvoice/createAndIssue`

交付物：

1. `ServiceFeeInvoiceCreateReq`
2. Controller 接口
3. Service 创建逻辑
4. 对应单元测试或集成测试

验收标准：

1. 能按入参创建主记录
2. 创建时生成 20 位 `fpqqlsh`
3. 创建时落原始请求报文和报文摘要
4. 测试用例通过

### TASK-004 实现乐企开票调用与同步结果回写

目标：

1. 封装 `GP_FPKJ` 调用
2. 处理同步成功、异步处理中、同步失败三类返回

交付物：

1. `LeqInvoiceClient`
2. 调用配置
3. 状态回写逻辑
4. 对应单元测试或集成测试

验收标准：

1. `CODE=0000` 时能回写发票号码、代码、日期、下载地址
2. `CODE=1000` 时能回写 `lsh` 并保留开票中状态
3. 非成功返回时能回写 `return_code`、`return_message`、`fail_reason`
4. 测试用例通过

### TASK-005 实现失败重试能力

目标：

1. 仅允许失败记录重试
2. 严格复用原 `fpqqlsh` 和原报文

建议接口：

1. `POST /system/mhApi/serviceFeeInvoice/{invoiceId}/retry`

交付物：

1. 重试 Service
2. 商户侧 Controller
3. 重试日志落库逻辑
4. 对应单元测试或集成测试

验收标准：

1. 非失败状态不可重试
2. 超过 3 次不可重试
3. 重试后不新增新的主发票记录
4. 重试日志可追溯
5. 测试用例通过

### TASK-006 实现商户端发票记录列表查询接口

目标：

1. 提供 merchant 端发票记录查询
2. 输出字段统一使用正式发票模型命名

建议接口：

1. `GET /system/mhApi/serviceFeeInvoice/list`

交付物：

1. `ServiceFeeInvoiceQueryReq`
2. `ServiceFeeInvoiceVO`
3. 列表查询 SQL
4. 对应接口测试

验收标准：

1. 支持按开票时间、服务费汇总记录编码、发票号码、状态查询
2. 返回字段名与方案设计文档一致
3. 只返回当前登录商户有权查看的数据
4. 测试用例通过

### TASK-007 实现商户端下载地址查询接口

目标：

1. 提供成功发票的下载地址查询
2. 同时支持 `PDF / OFD / XML`

建议接口：

1. `GET /system/mhApi/serviceFeeInvoice/{invoiceId}/downloadOptions`

交付物：

1. 下载地址查询接口
2. 权限校验
3. 对应接口测试

验收标准：

1. 仅成功状态可下载
2. 仅返回当前商户可访问的记录
3. 返回 `pdfUrl`、`ofdUrl`、`xmlUrl`
4. 测试用例通过

### TASK-008 实现开票中记录异步结果处理

目标：

1. 处理 `CODE=1000` 场景
2. 补齐开票中记录终态

交付物：

1. 定时任务或异步补偿任务
2. 结果查询和状态回写逻辑
3. 对应任务测试

验收标准：

1. 能扫描 `invoice_status = 1` 的记录
2. 能把终态回写为成功或失败
3. 不会错误生成新的 `fpqqlsh`
4. 测试用例通过

说明：

1. 本任务方案先按轮询设计
2. 若研发最终冻结为回调方案，应保持表结构和对外接口不变，只调整内部实现
