# 影响分析 v2

需求：`REQ-003 ETC拓展平台结算服务费开票功能`

本文基于 `需求澄清.md`（现行）、原始材料和 `ExtendPlatform` 现有代码现状输出。

## 1. 现状结论

代码核对后的结论如下：

1. 商户端现有 [invoiceManage 页面](E:\\CodexSpace\ExtendPlatform\etcplus-ui-merchant\src\views\trans\settle\invoiceManage\index.vue) 仍是占位页，数据源来自结算明细，不是真实发票记录。
2. 管理端现有 [TransferBillController](E:\\CodexSpace\ExtendPlatform\etcplus-modules\etcplus-system\src\main\java\com\etcplus\system\manage\trans\controller\TransferBillController.java) 仍是旧的人工登记/审核逻辑，不适合承接本期乐企直连开票。
3. [MerchantInvoice](E:\\CodexSpace\ExtendPlatform\etcplus-modules\etcplus-system\src\main\java\com\etcplus\system\business\merchant\domain\MerchantInvoice.java) 和 `etcplus_merchant_invoice` 只能提供商户开票资料，不能承接发票执行结果。
4. 当前代码中未检索到已落地的乐企 `GP_FPKJ`、`FPQQLSH`、下载地址或查询接口实现。

结论：本期应新增独立的“服务费发票执行模块”，不能直接复用旧发票流程。

## 2. 受影响模块

| 模块 | 影响判断 | 说明 |
| --- | --- | --- |
| 商户前台发票记录页 | 高 | 现页面需改造成真实发票记录页 |
| 后端发票执行服务 | 高 | 需新增乐企开具、查询、重试逻辑 |
| 发票记录数据模型 | 高 | 需新增服务费发票主表，并补足项目明细和查询结果字段 |
| 商户开票资料读取 | 中 | 作为购买方信息来源复用 |
| 前一流程待开票数据输出 | 高 | 需明确传入字段和调用时机 |
| 定时任务/异步处理 | 高 | 需处理 `CODE=1000` 和查询补偿 |

## 3. 核心影响点

### 3.1 接口影响

必须新增或补齐：

1. 前一流程调用的“创建并发起开票”接口。
2. 商户端发票记录列表接口。
3. 商户端失败重试接口。
4. 商户端下载地址查询接口。
5. 乐企开票接口接入。
6. 乐企发票查询接口接入。

### 3.2 数据影响

主表需覆盖：

1. 来源关联。
2. 商户快照。
3. 购销方快照。
4. 金额快照。
5. 项目明细固定字段。
6. `FPQQLSH/LSH`。
7. 请求报文快照。
8. 开票结果。
9. 查询结果与下载地址。
10. 重试控制。

### 3.3 页面影响

商户端页面需要从旧字段改为正式发票字段：

1. `serviceFeeRecordCode`
2. `invoiceStatus`
3. `failReason`
4. `retryCount`
5. `remainingRetryCount`
6. `invoiceNo`
7. `invoiceCode`
8. `pdfUrl`
9. `ofdUrl`
10. `xmlUrl`

字段命名应以后端正式模型为准，不沿用旧占位页命名。

## 4. 高风险项

| 风险 | 说明 | 控制建议 |
| --- | --- | --- |
| 重试与重开混淆 | 会造成重复开票 | 全链路统一使用“重试”术语 |
| `FPQQLSH` 误生成新值 | 会破坏幂等 | 同一发票记录只生成一次 |
| 本流程二次算税额 | 会与前一流程尾差规则冲突 | 本流程只消费冻结金额 |
| `CODE=1000` 无查询补偿 | 状态可能长期停留开票中 | 必须落查询接口或定时补偿 |
| 下载地址缺失 | 成功后无法下载 | 成功回写时优先取开具结果，不足时走查询补齐 |

## 5. 影响分析结论

1. 代码现状不足以直接承接本需求，需要新增独立后端模块和正式发票表。
2. 本期不仅是“开票”，还包括“开票后查询补齐”和“商户记录管理”。
3. `03-方案设计` 必须同时覆盖前端、后端、数据模型、异步补偿与接口落位。
