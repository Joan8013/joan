# 方案设计 v5（最终版）

需求：`REQ-003 ETC拓展平台结算服务费开票功能`


## 文档说明

本文档为最终设计基线，所有口径已全部定死，无待确认项，可作为开发直接开工的依据。


## 1. 方案目标

本期在 ExtendPlatform 中落一条完整的服务费发票执行链路：

1. 承接已审核通过的开票申请单。
2. 按申请单已冻结的拆票结果，生成 1-2 条单张发票执行记录。
3. 调用乐企开票接口。
4. 通过定时补偿调用乐企查询接口，补齐最终结果与下载地址。
5. 为商户提供发票记录查询、失败重试、成功下载能力。


## 2. 核心业务关系

### 2.1 上下游对象关系

| 层级 | 对象 | 说明 |
| :--- | :--- | :--- |
| 1 | 服务费汇总记录 | 对账单层级，一条记录 |
| 2 | 开票申请单 | 对应一条服务费汇总记录 |
| 3 | 发票执行记录 | 一张申请单可拆成 **1-2 张**发票，每张一条执行记录 |

**映射关系**：

- `apply_id / apply_no` → 关联申请单
- `split_seq / split_total_count` → 区分同一申请单下的第 1 张/第 2 张发票
- `recon_bill_id / recon_bill_no` → 回溯服务费汇总记录

### 2.2 审核信息处理

审核信息与申请信息放在同一张业务表中，因此：

1. 发票执行表不再单独关联审核单。
2. 是否具备开票资格，以申请单自身审核通过状态为准。


## 3. 代码现状判断

结合 `ExtendPlatform` 当前代码：

1. 商户端现有 `invoiceManage` 页面仍是占位页，需要整体替换为真实发票记录页。
2. 旧 `TransferBill` 体系属于人工登记/审核历史链路，不适合承接本期乐企直连开票。
3. 商户开票资料表只可作为购买方资料来源，不能承接发票执行结果。
4. 当前未发现已落地的乐企开票和查询实现。

**结论**：本期仍需新增独立“服务费发票执行模块”。

## 6. 金额计算规则

### 6.1 基础公式

| 字段 | 计算规则 | 精度 |
| :--- | :--- | :--- |
| 价税合计（`jshj_amount`） | 上游传入 | 元，2位小数 |
| 合计金额（`hjje_amount`） | `价税合计 ÷ 1.06`，四舍五入 | 元，2位小数 |
| 合计税额（`hjse_amount`） | `价税合计 - 合计金额` | 元，2位小数 |

### 6.2 尾差处理规则（强制调平）

当拆票后各张发票分别计算的不含税合计与整开一张的结果存在差异时，**强制调平**，尾差落在**最后一张发票**上。

**调平步骤**：

1. 前 N-1 张发票按正常除法计算（价税合计 ÷ 1.06，四舍五入，税额 = 价税合计 - 不含税）。
2. **最后一张发票的价税合计保持不变**（仍等于拆分时的金额）。
3. **最后一张发票的不含税金额** = 整开一张的不含税金额 - 前 N-1 张不含税金额之和。
4. **最后一张发票的税额** = 该张价税合计 - 该张不含税金额。

**校验规则**：

- Σ(各张价税合计) = 对账单总金额
- Σ(各张不含税) = 整开一张的不含税金额（四舍五入后）
- Σ(各张税额) = 整开一张的税额（四舍五入后）
- 每张票内：价税合计 = 不含税 + 税额

**调平示例**：

对账单总额 100.00 元，拆成 3 张：33.33、33.33、33.34。整开基准：不含税 94.34 / 税额 5.66。

| 发票 | 价税合计 | 不含税 | 税额 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| ① | 33.33 | 31.44 | 1.89 | 正常计算 |
| ② | 33.33 | 31.44 | 1.89 | 正常计算 |
| ③ | **33.34** | **31.46** | **1.88** | **尾差调平** |
| **合计** | **100.00** | **94.34** | **5.66** | ✅ 完全对齐 |

**关键原则：价税合计永远不变，只调不含税和税额，确保总额始终等于对账单金额。**

## 9. 状态与重试设计

### 9.1 发票执行表状态

| 状态值 | 状态名 | 说明 |
| :--- | :--- | :--- |
| 0 | 待开票 | 初始状态，已落记录未调用乐企 |
| 1 | 开票中 | 已调用乐企，`CODE=1000` 或异步等待中 |
| 2 | 开票成功 | 开票完成，有发票代码/号码/下载地址 |
| 3 | 开票失败 | 开票失败，允许重试（最多3次） |

### 9.2 重试设计

| 规则 | 说明 |
| :--- | :--- |
| 允许重试的条件 | 仅状态=开票失败的记录 |
| 最大重试次数 | **3次**（`max_retry_count` = 3） |
| 幂等键 | 重试复用原 `FPQQLSH` |
| 请求报文 | 重试复用原 `request_payload` |
| 主记录 | 重试不新增主记录，仅更新 `retry_count` 和状态 |
| 日志 | 每次重试写入日志表（`etcplus_recon_bill_invoice_retry_log`） |

### 9.3 申请单汇总状态

申请单状态由**上游负责汇总回写**，本模块提供按 `apply_id` 汇总执行状态的查询接口供上游调用。

| 10 | 开票时间 | `invoice_date` |
| 11 | 操作 | 成功=下载，失败=重试 |

### 10.3 列表规则

| 规则 | 说明 |
| :--- | :--- |
| 失败原因展示 | 列表页只展示最新一次失败原因 |
| 重试次数展示 | **不展示**已重试次数和剩余次数 |
| 下载格式 | 成功时支持 `PDF/OFD/XML` 三种格式选择下载 |
| 重试操作 | 失败时显示重试按钮 |
| 大字段禁止 | 列表接口**禁止返回** `request_payload` 和 `item_detail_payload` |
| SQL 规范 | 列表查询**禁止** `SELECT *` |


## 11. 已冻结口径（完整清单）

| 序号 | 确认项 | 结论 |
| :--- | :--- | :--- |
| 1 | 金额单位 | **元**，保留2位小数 |
| 2 | 税率 | 固定 **0.06** |
| 3 | 数量 | 固定 **1.000000**（6位小数） |
| 4 | 单价 | **动态计算**：单价 = 不含税金额 ÷ 数量，数量固定为1，即单价 = 不含税金额。由实际计算值决定，**总长度不超过15位，最多保留13位小数**。 |
| 5 | 尾差处理 | **强制调平**，尾差落在**最后一张发票**，价税合计**不变**，只调不含税和税额 |
| 6 | 表名 | `etcplus_recon_bill_invoice` |
| 7 | 唯一键 | **两组都保留**：`uk_apply_id_seq` + `uk_apply_no_seq` |
| 8 | `remark` 类型 | `varchar(240)` |
| 9 | `request_payload` 类型 | `mediumtext` |
| 10 | `item_detail_payload` 类型 | `mediumtext` |
| 11 | 日志表 | **保留**：`etcplus_recon_bill_invoice_retry_log` |
| 12 | 列表查询 | 严禁返回 `request_payload`、`item_detail_payload` |
| 13 | 入参金额 | 上游传入**元**（不是分），本模块不做单位换算 |
| 14 | `remark` 截断 | 上游生成并截断（专票184/普票138），本模块校验长度，超长则拒绝 |
| 15 | 申请单汇总状态回写 | 上游负责，本模块提供查询接口 |
| 16 | `apply_item_id` | 不加 |
| 17 | `biz_nature_mod` 冗余 | 不加 |
| 18 | 单价入参 | 不入参，本模块按公式自动计算 |
| 19 | 固定配置字段 | 销售方信息、税率、开票人、项目名称、规格型号、单位、数量、税收分类编码统一配置，不入参 |
| 20 | 旧开票功能切换 | 新功能上线后，由业务确认时间节点（以划账时间为准），新旧并行期间避免重复开票 |

## 13. 结论

1. 本期模型为 **“申请单驱动 + 单张发票执行明细”**。
2. `split_seq` 是区分同一申请单下第1张/第2张发票的关键字段。
3. 尾差处理规则已冻结：**强制调平，最后一张发票调平，价税合计不变**。
4. 单价规则已冻结：**动态计算，不限定小数位数，满足乐企总长度≤15位、最多13位小数**。
5. 所有入参/计算/存储口径已全部定死。
6. **本文档可作为进入开发前的最终设计基线。**
