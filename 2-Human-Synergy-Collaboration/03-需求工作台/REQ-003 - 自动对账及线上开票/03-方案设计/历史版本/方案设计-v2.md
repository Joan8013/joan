# 方案设计 v2

需求：`REQ-003 ETC拓展平台结算服务费开票功能`

本文基于以下内容输出：

1. `01-需求澄清/需求澄清-v2.md`
2. `02-影响分析/影响分析-v1.md`

4. `ExtendPlatform` 当前代码结构
5. 乐企开票接口文档 `GP_FPKJ` 及相关结果查询能力

本文目标是输出一份可进入开发拆分的前后端方案，不只停留在建表层面。

## 1. 方案目标

本期在 ExtendPlatform 中新增一条独立的“服务费开票执行与结果管理”链路：

1. 接收前一流程已拆分并冻结好的待开票数据。
2. 调用乐企 `GP_FPKJ` 发起数电票开具。
3. 保存开票状态、票面结果、失败原因和下载地址。
4. 为商户前台提供发票记录查询、失败重试、成功下载能力。

本期明确不做：

1. 审核流
2. 拆票规则生成
3. 红冲、作废、换票
4. 商户在线编辑开票字段
5. 开票报文项目明细手工维护

## 2. 业务边界与关键口径

### 2.1 边界

前一流程负责：

1. 拆票
2. 发票类型确定
3. 开票金额冻结
4. 项目明细 `COMMON_FPKJ_XMXX` 生成
5. 判定哪些记录具备开票资格

本流程负责：

1. 创建发票执行记录
2. 生成并持久化 `FPQQLSH`
3. 组装并保存乐企请求报文
4. 调用乐企开票接口
5. 管理状态、重试、下载

### 2.2 术语统一

1. 本文统一使用“重试”，不使用“重开”。
2. “重试”定义为：复用同一 `FPQQLSH` 和同一请求报文再次发起请求。
3. 本期不涉及“作废后重新开具新票”的业务动作。

### 2.3 乐企关键口径

1. `FPQQLSH`：20 位开票请求流水号，幂等主键。
2. `LSH`：异步流水号，用于异步结果跟踪，不替代 `FPQQLSH`。
3. 失败重试必须复用原 `FPQQLSH` 和原报文，否则存在重复开票风险。

## 3. 现有代码现状判断

结合 `ExtendPlatform` 代码，以下能力可参考但不能直接承接本期主流程：

2. `etcplus_merchant_invoice` 等资料表

定位：

### 3.2 交易发票能力

已有：

1. `etcplus_trans_invoice`
2. 停车交易发票查询 Mapper

定位：

1. 来源对象是交易流水，不是服务费待开票记录。
2. 不能承接本期状态、重试、幂等和下载管理。

### 3.3 旧申请审核链路

已有：

1. `TransferBillController`
2. `TransferBill* / TransferBillTotal*`

定位：

1. 属于旧的申请、审核、手工登记票号流程。
2. 与本期“前一流程冻结字段后直接直连乐企开票”的模式不匹配。

### 3.4 商户前台占位页面

已有页面：

1. `etcplus-ui-merchant/src/views/trans/settle/invoiceManage/index.vue`

1. 仍使用结算明细数据源。
2. 操作按钮是占位跳转，不是实际发票操作。
3. 字段名与正式发票模型不一致。

结论：

1. 本期应新增独立“服务费开票模块”。
2. 前端可复用该页面落点，但必须改为真实发票记录页。

## 4. 总体方案

### 4.1 模块交互方式

本模块不主动去“扫待开票记录”，而是对外提供一个明确的开票入口，由前一流程在完成拆票并冻结字段后主动调用。

建议交互方式：

1. 前一流程完成拆票，形成单张待开票记录。
2. 前一流程调用本模块“创建并发起开票”接口。
3. 本模块创建 `etcplus_service_fee_invoice` 主记录，状态置为 `待开票`。
4. 本模块生成 `FPQQLSH`，固化请求报文并发起 `GP_FPKJ`。
5. 根据同步返回结果更新状态。
6. 若进入异步处理中，再由异步处理机制补齐终态。

说明：

1. 这样可以明确责任边界。
2. 本模块不负责推断来源记录，也不负责决定何时可以开票。

### 4.2 模块落位建议

建议在 `etcplus-modules/etcplus-system` 下新增独立业务包：

1. 商户前台 Controller：
2. `com.etcplus.system.split.merchant.invoice.controller`
3. 后端管理查询 Controller：
4. `com.etcplus.system.manage.invoice.controller`
5. 业务 Service / Domain / Mapper：
6. `com.etcplus.system.business.invoice.*`

这样做的原因：

1. 保持与现有 merchant / manage 双端结构一致。
2. 不污染旧 `settle`、`trans`、`TransferBill` 包。
3. 后续如果扩展其他发票能力，也有独立承载空间。

## 5. 后端设计

### 5.1 核心对象

本期按“够用、可实现、不过度拆分”控制对象规模，建议新增：

1. `ServiceFeeInvoice`
2. `ServiceFeeInvoiceRetryLog`
3. `ServiceFeeInvoiceCreateReq`
4. `ServiceFeeInvoiceQueryReq`
5. `ServiceFeeInvoiceVO`
6. `ServiceFeeInvoiceService`
7. `ServiceFeeInvoiceMapper`
8. `ServiceFeeInvoiceRetryLogMapper`
9. `LeqInvoiceClient`

对象职责：

1. `ServiceFeeInvoice`
   对应主表 `etcplus_service_fee_invoice`，保存发票业务快照和执行结果。
2. `ServiceFeeInvoiceRetryLog`
   保存首次发起和每次重试的调用留痕。
3. `ServiceFeeInvoiceCreateReq`
   由前一流程调用本模块开票入口时传入，字段只承接已冻结的待开票数据。
4. `ServiceFeeInvoiceQueryReq`
   商户前台列表查询入参对象。
5. `ServiceFeeInvoiceVO`
   商户前台列表和详情返回对象，字段命名以后端正式模型为准。
6. `ServiceFeeInvoiceService`
   负责创建发票记录、发起开票、重试、查询、下载逻辑。
7. `ServiceFeeInvoiceMapper`
   主表数据库访问层。
8. `ServiceFeeInvoiceRetryLogMapper`
   重试日志数据库访问层。
9. `LeqInvoiceClient`
   封装与乐企的接口交互。

当前不建议一开始就拆出：

1. `LeqInvoiceRequestBuilder`
2. `ServiceFeeInvoiceAsyncService`
3. `ServiceFeeInvoiceDownloadReq`

原因：

1. 当前需求规模下收益不高。
2. 后续复杂度增加时，再自然下沉即可。

### 5.2 发票主数据口径

本期已经确认的开票核心字段只有以下内容：

1. `buyerName`
2. `buyerTaxNo`
3. `sellerName`
4. `sellerTaxNo`
5. `jshjAmount`
6. `hjjeAmount`
7. `hjseAmount`
8. `taxRate`
9. `invoiceType`
10. `drawerName`

补充原则：

1. `hjjeAmount`、`hjseAmount` 可以由前一流程直接传入，也可以由本模块按固定公式校验计算。
2. 拆票尾差归属由前一流程负责，本模块不再二次修正拆票结果。
3. `invoiceType` 统一存乐企 `FPLXDM` 值，如 `030`、`032`。

### 5.3 状态机设计

主状态使用 4 个状态：

1. `0-待开票`
2. `1-开票中`
3. `2-开票成功`
4. `3-开票失败`

状态定义：

1. `待开票`：本模块已创建发票记录，但尚未实际调用 `GP_FPKJ`。
2. `开票中`：已调用 `GP_FPKJ`，同步返回 `CODE=1000` 或尚未拿到最终结果。
3. `开票成功`：同步或异步终态返回成功，已拿到票面结果。
4. `开票失败`：同步或异步终态返回失败。

状态流转：

1. 创建记录后置 `待开票`
2. 调用乐企前更新为 `开票中`
3. `CODE=0000` 更新为 `开票成功`
4. `CODE=1000` 保持 `开票中`
5. 其他错误码更新为 `开票失败`
6. 人工重试后重新进入 `开票中`

### 5.4 幂等与重试设计

幂等规则：

1. `FPQQLSH` 长度固定 20 位。
2. 同一发票主记录只生成一次 `FPQQLSH`。
3. `FPQQLSH` 全局唯一。
4. 重试必须复用原 `FPQQLSH`。

重试规则：

1. 仅状态为 `开票失败` 的记录允许重试。
2. 最大重试次数为 3。
3. 重试时复用原 `request_payload` 和原项目明细快照。
4. 不允许修改金额、抬头、税号、发票类型、明细。
5. 重试只更新同一条主记录，不新增新的发票主记录。

并发控制建议：

1. 重试前校验 `invoice_status = 3`。
2. 条件更新时带状态条件和重试次数条件。
3. 条件更新失败时提示“记录状态已变化，请刷新后重试”。

### 5.5 乐企接口调用设计

必须对接：

1. `GP_FPKJ`

建议预留：

1. 开票结果查询能力
2. 下载地址查询能力

同步返回处理：

1. `CODE=0000`：保存 `invoice_code`、`invoice_no`、`invoice_date`、`pdf_url`、`ofd_url`、`xml_url`，状态改成功。
2. `CODE=1000`：保存 `LSH`，状态保持开票中。
3. 其他错误码：保存 `return_code`、`return_message`、`fail_reason`，状态改失败。

### 5.6 异步结果处理设计

本期建议在方案层同时保留“轮询优先、回调预留”的口径。

#### 方案 A：轮询

优点：

1. 落地路径更直接。
2. 对现有基础设施依赖较少。

代价：

1. 需要定时任务扫描开票中记录。
2. 需要控制轮询频率和超时策略。

建议口径：

1. 扫描 `invoice_status = 1` 的记录。
2. 轮询间隔建议 2 到 5 秒。
3. 最大轮询时长建议 3 到 5 分钟。

#### 方案 B：回调

优点：

1. 结果获取更及时。
2. 系统主动查询压力更小。

代价：

1. 需要回调地址治理、验签、幂等处理和失败补偿。
2. 需确认现网基础设施是否满足暴露和回调接入条件。

本版结论：

1. 方案设计先按“轮询可落地”输出。
2. 接口和表字段上预留回调兼容空间。
3. 最终技术落地方式由研发结合基础设施再冻结。

### 5.7 下载设计

本期目标是让商户可下载成功发票，不引入额外的票据生命周期管理。

后端保存：

1. `pdf_url`
2. `ofd_url`
3. `xml_url`

前端展示建议：

1. 成功记录展示“下载发票”入口。
2. 点击后弹出格式选择，支持 `PDF / OFD / XML`。
3. 默认选中 `PDF`。

后端接口返回建议：

1. 返回各格式可用地址。
2. 前端按地址是否为空控制可选项。

是否代理下载：

1. 若乐企地址可直接访问，则直接返回 URL。
2. 若存在鉴权、签名或跨域问题，再补后端代理下载能力。

查询条件建议：

1. 开票时间范围
2. 服务费汇总记录编码

返回字段建议：

1. `invoiceId`
2. `serviceFeeRecordCode`
3. `merchantId`
4. `merchantName`
5. `buyerName`
6. `buyerTaxNo`
7. `invoiceType`
8. `jshjAmount`
9. `invoiceStatus`
10. `failReason`
11. `invoiceCode`
12. `invoiceNo`
13. `invoiceDate`
14. `retryCount`
15. `maxRetryCount`
16. `canRetry`
17. `canDownload`
18. `pdfUrl`
19. `ofdUrl`
20. `xmlUrl`

字段命名原则：

1. 前端返回字段统一以发票主表和 `ServiceFeeInvoiceVO` 为准。
2. 不兼容旧占位页面中的临时字段名。

例如：

1. 使用 `serviceFeeRecordCode`，不使用 `reconBillNo`
2. 使用 `invoiceStatus`，不使用 `itemStatus`
3. 使用 `buyerName`、`buyerTaxNo`，不使用 `invoiceTitle`、`taxpayerNo`
4. 使用 `failReason`，不使用 `failureReason`

#### 2. 失败重试

`POST /system/mhApi/serviceFeeInvoice/{invoiceId}/retry`

处理逻辑：

1. 校验当前登录商户是否有权操作。
2. 校验状态必须为失败。
3. 校验重试次数未超限。
4. 复用原 `FPQQLSH` 和原报文重发。

#### 3. 下载发票

`GET /system/mhApi/serviceFeeInvoice/{invoiceId}/downloadOptions`

返回建议：

1. `invoiceId`
2. `pdfUrl`
3. `ofdUrl`
4. `xmlUrl`
5. `canDownload`

说明：

1. 本期先返回下载地址集合。
2. 若后续要做代理下载，再新增代理接口。

## 10. 方案结论

1. 本期应新增独立“服务费开票模块”，不挂靠旧交易发票或旧审核流程。
2. 后端核心是“一个开票入口 + 一张主表 + 一张重试日志表 + 一组商户前台接口 + 一套异步终态处理机制”。
3. 前端核心是把现有 `invoiceManage` 页面改造成真实发票记录页，并统一切换到正式发票字段命名。
4. `etcplus_service_fee_invoice` 需要的字段不应无限扩张，但也必须覆盖业务快照、幂等执行、状态结果和下载管理这四类必要信息。
