# 发票表设计 v2

需求：`REQ-003 ETC拓展平台结算服务费开票功能`

本文只聚焦“服务费开票执行 + 发票记录管理”所需的数据表设计。

## 1. 设计结论先说

`etcplus_service_fee_invoice` 需要保留的字段不应该很多，但也不能只剩票面号码几个字段。

本期建议把字段收敛成 4 组：

1. 来源关联字段
2. 已确认的开票业务快照字段
3. 乐企幂等与请求报文字段
4. 开票结果与下载管理字段

一句话结论：

这张表要做的是“服务费发票执行结果表”，不是“商户开票资料表”，也不是“结算申请表”。

## 2. 设计前提

1. 本期不处理审核流程。
2. 本期不处理拆票规则，拆票结果由前一流程产出。
3. 本流程只消费前一流程生成的待开票数据。
4. 乐企开票主接口为 `GP_FPKJ`。
5. `FPQQLSH` 是幂等主键，长度固定 20 位。
6. 失败重试必须复用原 `FPQQLSH` 和原报文。
7. 商户前台只需要发票记录查询、失败重试、成功下载。
8. 本期已确认的核心开票字段只有：
9. 购买方名称
10. 购买方纳税人识别号
11. 销售方名称
12. 销售方纳税人识别号
13. 价税合计
14. 合计金额
15. 合计税额
16. 税率
17. 发票类型
18. 开票人

## 3. 主表设计：`etcplus_service_fee_invoice`

### 3.1 表定位

一行代表一条待开票记录的开票执行结果。

说明：

1. 一条服务费汇总记录可以被前一流程拆成多条待开票记录。
2. 本表只认拆票后的单张待开票记录。
3. 一条待开票记录对应一条主发票记录。
4. 失败重试不新增主记录，只更新同一条主记录。

### 3.2 推荐字段清单

#### 3.2.1 来源关联字段

| 字段名 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `invoice_id` | bigint | 是 | 主键 |
| `merchant_id` | varchar(64) | 是 | 商户号 |
| `merchant_name` | varchar(128) | 是 | 商户名称快照 |
| `source_record_id` | varchar(64) | 是 | 前一流程待开票记录ID |
| `source_record_type` | varchar(32) | 是 | 来源记录类型，如 `SERVICE_FEE_APPLY_ITEM`，便于后续扩展 |
| `service_fee_record_code` | varchar(64) | 是 | 服务费汇总记录编码 |

#### 3.2.2 开票业务快照字段

| `seller_name` | varchar(300) | 是 | 销售方名称 |
| `seller_tax_no` | varchar(20) | 是 | 销售方纳税人识别号 |
| `jshj_amount` | decimal(18,2) | 是 | 价税合计 |
| `hjje_amount` | decimal(18,2) | 是 | 合计金额，不含税 |
| `hjse_amount` | decimal(18,2) | 是 | 合计税额 |
| `tax_rate` | decimal(8,6) | 是 | 税率，固定 `0.060000` |

| `drawer_name` | varchar(64) | 是 | 开票人 |

#### 3.2.3 幂等与请求字段

| 字段名 | 类型 | 必填 | 说明 |

#### 3.2.4 结果与管理字段

| 字段名 | 类型 | 必填 | 说明 |

| `return_message` | varchar(1000) | 否 | 乐企返回消息 |
| `fail_reason` | varchar(1000) | 否 | 页面友好失败原因 |
| `invoice_code` | varchar(32) | 否 | 发票代码 |
| `invoice_no` | varchar(32) | 否 | 发票号码 |

| `update_at` | datetime | 是 | 更新时间 |

### 3.3 当前明确不纳入主表的字段

以下字段不建议塞进主表：

1. 购买方地址、电话、开户行、银行账号
2. 销售方地址、电话、开户行、银行账号
3. 审核人、审核时间、审核意见
4. 红冲、作废、换票字段
5. 拆票规则、尾差分摊规则字段
6. 停车交易维度字段
7. 逻辑删除字段
8. 未确认用途的扩展 JSON 字段

原因：

1. 这些都不是本期必需。
2. 硬塞进去会把新表又变成旧流程表。

## 4. 关键约束建议

建议至少增加以下约束和索引：

1. 主键：`invoice_id`
2. 唯一键：`uk_fpqqlsh (fpqqlsh)`
3. 普通索引：`idx_merchant_status (merchant_id, invoice_status)`
4. 普通索引：`idx_service_fee_record_code (service_fee_record_code)`
5. 普通索引：`idx_source_record (source_record_id, source_record_type)`
6. 普通索引：`idx_invoice_no (invoice_no)`
7. 普通索引：`idx_create_at (create_at)`

说明：

1. `fpqqlsh` 唯一约束是最关键约束。
2. 不建议对 `service_fee_record_code` 加唯一约束，因为一条汇总记录可能拆成多张发票。
3. 如果前一流程能保证 `source_record_id + source_record_type` 唯一，也可以增加唯一约束。

## 7. 字段取舍说明

### 7.1 为什么还需要 `request_payload`

因为乐企要求失败重试必须复用原报文。

不存原报文会带来三个问题：

1. 无法保证重试真的原样发送。
2. 无法联调排障。
3. 遇到超时和 `9992`、`9999` 时无法可靠复现。

### 7.2 为什么不把所有购销方资料都塞进来

因为当前需求只确认了名称和税号。

本表是执行结果表，不是完整票面资料档案表。未确认要传的地址、电话、银行信息，不建议为了“也许以后会用”提前入表。

### 7.3 为什么不加逻辑删除字段

这是一张财务票据执行结果表。

如果逻辑删除，会让已经发生过的开票行为在系统中“消失”，不利于追溯和对账。本期也没有“删除发票记录”的业务需求，因此不建议增加 `deleted` 字段。

## 8. 最终建议

如果按当前需求和乐企接口文档收敛，我的建议是：

1. 必建 `etcplus_service_fee_invoice`
2. 建议建 `etcplus_service_fee_invoice_retry_log`
3. 主表字段保持精简，但必须覆盖来源、业务快照、幂等执行、状态结果、下载管理
4. 不复用旧资料表、旧交易发票表、旧审核申请表

一句话总结：

`etcplus_service_fee_invoice` 不需要做成“大而全”，但现在这版 v2 的字段量基本是刚好够用的，不算虚胖。
