# 方案设计 v5

需求：`REQ-003 ETC拓展平台结算服务费开票功能`

本文基于最新财务字段确认、乐企 `GP_FPKJ` 接口口径、以及现有申请单结构重写，作为开发基线稿。

## 1. 方案目标

本期在 ExtendPlatform 中落一条完整的服务费发票执行链路：

1. 承接已审核通过的开票申请单。
2. 按申请单已冻结的拆票结果，生成 1-2 条单张发票执行记录。
3. 调用乐企开票接口。
4. 通过定时补偿调用乐企查询接口，补齐最终结果与下载地址。
5. 为商户提供发票记录查询、失败重试、成功下载能力。

## 2. 核心业务关系

### 2.1 上下游对象关系

本期对象关系应理解为：

1. 一条服务费汇总记录
2. 对应一张开票申请单
3. 一张申请单可拆成 1-2 张发票
4. 发票执行表按单张发票一条记录落库

映射关系：

1. `apply_id / apply_no` 对应申请单
2. `split_seq / split_total_count` 区分同一申请单下的第 1 张/第 2 张发票
3. `recon_bill_id / recon_bill_no` 回溯服务费汇总记录

### 2.2 与现有代码字段的映射约定

结合 `ExtendPlatform` 当前代码，现有老链路里已经存在的关键字段主要是：

1. 申请单号：`bill_apply_no`
2. 申请单主键：`id`
3. 申请单状态：`bill_state`
4. 服务费汇总金额：`service_real_amt`
5. 业务性质：`biz_nature`

本期新增发票执行表仍建议使用更清晰的新领域字段命名，但在接入上游时应明确以下映射：

| 新发票执行表字段 | 现有代码字段来源 | 说明 |
| --- | --- | --- |
| `apply_id` | 申请单表 `id` | 强关联键 |
| `apply_no` | 申请单表 `bill_apply_no` | 业务追踪键 |
| `biz_nature` | 上游表 `biz_nature` | 代码现状为 `Integer`，`1=正常交易`、`2=助缴` |
| `merchant_name` | 申请单/商户表 `merchant_name` | 发票表落快照 |
| `buyer_name` | 商户开票信息 `invoice_unit_name` 或企业信息 `enterprise` | 以上游冻结值为准 |
| `buyer_tax_no` | 商户开票信息/企业信息 `invoice_tax_number` | 以上游冻结值为准 |

说明：

1. `recon_bill_id / recon_bill_no` 属于本期新领域字段，现有老链路未直接提供同名字段时，由上游在新申请流程中显式传入。
2. 发票执行表不强行沿用 `bill_apply_no` 之类旧命名，避免把“申请汇总对象”和“单张发票执行对象”混在一起。

### 2.3 审核信息处理

由于审核信息与申请信息放在同一张业务表中，因此：

1. 发票执行表不单独关联审核单
2. 是否具备开票资格，以申请单自身审核通过状态为准

## 3. 财务字段与乐企字段映射

## 4. 金额计算规则

### 4.1 已冻结口径

1. `JSHJ`：由上游传入，单位元，2位小数。
2. `HJJE`：由本模块按 `JSHJ ÷ 1.06` 计算，四舍五入保留2位小数。
3. `HJSE`：由本模块按 `JSHJ - HJJE` 计算，保留2位小数。

### 4.2 尾差处理

已确认采用方案 A：

1. 每张发票分别按公式独立计算。
2. 不强制调平。
3. 拆票后与整开一张产生的尾差允许存在。

## 7. 接口设计

### 7.1 上游开票入口

接口：

`POST /reconBillInvoice/createAndIssue`

入参为申请单维度：

1. `applyId`：开票申请主键ID
2. `applyNo`：开票申请单号
3. `reconBillId`：服务费汇总记录主键ID
4. `reconBillNo`：服务费汇总记录编号
5. `merchantId`：商户ID
6. `merchantName`：商户名称快照
7. `bizNature`：业务性质，平台业务口径：助缴、正常交易
8. `splitTotalCount`：拆票张数，1或2
9. `invoiceList`：单张发票列表

单张发票列表每项：

1. `splitSeq`：第几张发票，1或2
2. `invoiceType`：发票类型，030=数电普票，032=数电专票
3. `buyerName`：购买方名称
4. `buyerTaxNo`：购买方纳税人识别号
5. `jshjAmount`：该张发票价税合计，元，2位小数
6. `remark`：备注，由上游按乐企规则生成

说明：

1. 固定配置字段由系统读取配置，不入参。
2. `hjjeAmount`、`hjseAmount` 由本模块按公式计算，不入参。
3. `bizNature` 入参建议沿用现有代码口径：`1=正常交易`、`2=助缴`。

### 7.2 商户端接口

1. `GET /mhApi/merchant/reconBillInvoice/list`
2. `POST /mhApi/merchant/reconBillInvoice/{id}/retry`
3. `GET /mhApi/merchant/reconBillInvoice/{id}/downloadOptions`

返回字段统一以后端正式模型为准，不沿用旧占位页字段名。

## 8. 乐企调用设计

### 8.1 开票接口

每条单张发票执行记录单独调用一次乐企开票接口：

1. 先落主记录
2. 生成 `FPQQLSH`
3. 固化请求报文
4. 写入重试日志表，记录首次开票动作
5. 组装乐企固定字段与动态字段
6. 发起开票

### 8.2 查询接口

本期查询接口只用于定时补偿：

1. 补齐 `CODE=1000` 的最终结果
2. 补齐下载地址
3. 校验最终票面信息

不设计人工触发查询入口。

## 9. 状态设计

### 9.1 发票执行表状态

仍保持 4 个：

1. 待开票
2. 开票中
3. 开票成功
4. 开票失败

### 9.2 申请单汇总状态

申请单自己的状态不放进发票执行表。

已确认：

1. 由上游负责汇总回写申请单状态
2. 本模块提供发票执行结果查询能力

## 10. 重试设计

1. 仅失败记录允许重试
2. 最大 3 次
3. 重试复用原 `FPQQLSH`
4. 重试复用原报文
5. 重试不新增主记录
6. 每次重试必须新增一条日志表记录
7. 日志表字段至少包括：
   - `invoice_id`
   - `retry_no`
   - `action_type`
   - `request_payload_snapshot`
   - `response_code`
   - `response_message`
   - `trigger_by`
   - `trigger_at`

6. 列表查询禁止 `SELECT *`

## 12. 已冻结口径

1. 申请单汇总状态由上游负责回写。
2. `quantity` 固定传 `1.000000`，保留6位小数。
3. `unit_price` 固定传 `3581.103773584905`，保留15位小数。
4. `remark` 由上游生成并满足乐企长度要求，本模块透传。
5. `HJJE/HJSE` 由本模块计算。
6. 尾差处理采用方案 A，不调平。

## 13. 结论

1. 本期真实模型已收敛为“申请单驱动 + 单张发票执行明细”。
2. 上游负责传动态字段，本模块负责固定配置和金额计算。
3. 发票执行表必须保留关键快照字段，不能依赖事后联表追值。
4. 该版本已可作为开发可开工的基线稿。
