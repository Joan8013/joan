# 发票表设计 v4

需求：`REQ-003 ETC拓展平台结算服务费开票功能`

本版按最新已确认前提重写：

1. 一条服务费汇总记录可以开 1-2 张发票。
2. 商户先提交开票申请，业务及财务审核信息与申请信息在同一张表中。
3. 一张申请单可对应 1-2 张发票执行记录。
4. 发票执行表不再单独关联审核单。

## 1. 设计结论

发票执行表应理解为：

`申请单 -> 单张发票执行明细表`

也就是说：

1. 申请单是上游汇总对象。
2. 发票表是一张单张发票执行明细表。
3. 同一 `apply_id/apply_no` 下，最多产生 2 条发票记录。

## 2. 关键判断

### 2.1 不再保留独立审核单字段

由于审核信息已经和申请信息放在同一张业务表中，因此不再需要：

1. `audit_id`
2. `audit_no`

### 2.2 不再引入 `apply_item_id`

根据你给的最新截图和反馈，上游申请表没有明细粒度字段，只有申请单粒度。

因此本版不再引入：

1. `apply_item_id`

### 2.3 如何区分同一申请单下的两张发票

既然一张申请单可对应 1-2 张发票执行记录，就必须补：

1. `split_seq`
2. `split_total_count`

这是区分“同一申请单下第1张/第2张发票”的最小必要字段。

## 3. 主表建议

表名最终定为：

`etcplus_recon_bill_invoice`

理由：

1. 延续 `ExtendPlatform` 的 `etcplus_` 前缀命名习惯。
2. `recon_bill` 明确指向服务费汇总记录。
3. `invoice` 明确表明这是发票执行表。
4. 语义已经足够清晰，不需要再加 `detail` 或 `execution` 后缀。

## 5. 约束建议

### 5.1 必要约束

1. 主键：`id`
2. 唯一键：`uk_fpqqlsh (fpqqlsh)`
3. 唯一键：`uk_apply_id_seq (apply_id, split_seq)`
4. 唯一键：`uk_apply_no_seq (apply_no, split_seq)`

### 5.2 关于 `apply_no`

1. `apply_no` 应保留，用于业务追踪、接口报文和页面检索。
2. `apply_id` 仍是数据库内部更稳的强关联键。
3. 两组唯一键都保留，不删不减。
4. `uk_apply_id_seq (apply_id, split_seq)` 用于代码关联、更新、JOIN 和主流程控制。
5. `uk_apply_no_seq (apply_no, split_seq)` 用于业务排查和运维定位。
6. 一张申请单最多 2 条发票记录，索引开销极低，双重唯一约束可以兜底防止数据错乱。

### 5.3 普通索引

1. `idx_apply_no (apply_no)`
2. `idx_recon_bill_id (recon_bill_id)`
3. `idx_merchant_status (merchant_id, invoice_status)`
4. `idx_invoice_no (invoice_no)`

### 5.4 大字段类型定稿

| 字段 | 最终类型 | 定稿说明 |
| --- | --- | --- |
| `remark` | `varchar(240)` | 乐企备注最大 240 字符，业务侧实际口径为专票 184 / 普票 138，240 足够且不会超限 |
| `request_payload` | `mediumtext` | 开票报文通常几十 KB，极端情况几百 KB，`mediumtext` 16MB 上限足够，且比 `longtext` 更稳妥 |
| `item_detail_payload` | `mediumtext` | 项目明细快照大小级别与请求报文相近，统一使用 `mediumtext` |

## 6. 从申请表冗余到执行表的建议

建议冗余：

1. `biz_nature`
2. `merchant_name`
3. 申请时冻结的购销方信息

不建议冗余：

1. `apply_status`

原因：

1. `apply_status` 是申请单汇总口径。
2. `invoice_status` 是单张发票执行口径。
3. 两者职责不同，不应混到一张表里。

## 7. 大字段与查询性能约束

1. 列表查询禁止 `SELECT *`。
2. 列表接口禁止返回：
   - `request_payload`
   - `item_detail_payload`
3. 大字段仅允许在以下场景读取：
   - 详情查看
   - 失败重试
   - 联调排障
4. 若采用 MyBatis XML，应为列表查询和详情查询分开写字段清单或 `resultMap`。
5. 上述限制应同时写入：
   - 表设计文档
   - Mapper 查询字段清单
   - 代码注释或开发规范

## 8. 申请状态与执行状态分工

建议关系如下：

1. 发票执行表只维护单张发票的 `invoice_status`。
2. 申请单维护汇总状态，如处理中、部分成功、全部成功、全部失败。
3. 开票完成后，由定时任务或业务服务汇总执行表状态，回写申请单状态。

示例：

| 申请单 | 发票1 | 发票2 | 申请单汇总状态 |
| --- | --- | --- | --- |
| 1张 | 成功 | - | 全部成功 |
| 2张 | 成功 | 失败 | 部分成功 |
| 2张 | 失败 | 失败 | 全部失败 |

## 9. 分表策略建议

当前阶段建议先单表落地。

原因：

1. 当前需求仍处于首版落地阶段。
2. 业务量、查询模式、补偿任务频率还未稳定。

但应在设计上预留分表判断标准：

1. 当日均开票量持续高于 5000 单时，启动分表评估。
2. 当单表行数、补偿任务扫描成本、备份恢复时长明显上升时，进入分表方案设计。

可选方向：

1. 按月份分表
2. 按申请时间分表

## 10. 已冻结口径

1. 申请单汇总状态由上游负责回写，本模块提供执行结果查询能力。
2. `quantity` 固定传 `1.000000`，保留6位小数。
3. `unit_price` 固定传 `3581.103773584905`，保留15位小数。
4. `remark` 由上游生成并满足乐企长度要求，本模块透传。

## 11. 最终建议

如果用一句话收口：

1. 不要单独加审核单ID。
2. 不要再引入 `apply_item_id`。
3. 发票执行表按“申请单下的单张发票明细”设计。
4. 关键来源字段应为 `apply_id + apply_no + split_seq`。

这是现在最符合你实际表结构、也最容易落地的一版。

## 12. 重试日志表设计

日志表定死保留，表名：

`etcplus_recon_bill_invoice_retry_log`

### 12.1 为什么必须保留

1. 重试不新增主记录，但每次重试的请求和响应必须留痕。
2. 日志表是只增不改，对主表无影响。
3. 需要满足问题排查和审计要求。
4. 需要能回答“谁在什么时间触发了哪次开票/重试，结果是什么”。

### 12.2 推荐字段

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `invoice_id` | bigint | 关联主表 `id` |
| `retry_no` | tinyint | 第几次请求，1/2/3；首次开票也记录为第1次 |
| `action_type` | tinyint | 1=首次开票，2=重试 |
| `request_payload_snapshot` | mediumtext | 该次请求报文快照 |
| `response_code` | varchar(16) | 乐企返回码 |
| `response_message` | varchar(1000) | 乐企返回信息 |
| `trigger_by` | varchar(64) | 触发人（系统/商户/运营） |
| `trigger_at` | datetime(3) | 触发时间 |

### 12.3 关于报文快照

1. 理论上重试报文可复用主表 `request_payload`。
2. 但日志表建议仍保留 `request_payload_snapshot`。
3. 这样每次请求的留痕是自洽的，排查时不必反查主表历史状态。

### 12.4 设计结论

1. 日志表必须存在。
2. 日志表是留痕表，不承担主流程状态控制。
3. 主表记录当前状态，日志表记录每次动作历史。
