# 发票表设计 v1

需求：`REQ-003 ETC拓展平台结算服务费开票功能`

本文只聚焦“服务费开票执行 + 发票记录管理”所需的发票表设计，不展开接口实现、页面实现和任务拆分。

## 1. 设计前提

1. 本期不处理审核流程。
2. 本期不处理拆票规则，拆票结果由前一流程产出。
3. 本流程只消费前一流程生成的待开票数据，不重新决定发票类型、金额和项目明细。
4. 乐企开票主接口为 `GP_FPKJ`。
5. `FPQQLSH` 是开票请求幂等键，长度固定 20 位，失败重试必须复用原值和原报文。
6. 商户页面只需要看到已开过的发票记录，并根据状态做“失败重试 / 成功下载”。
7. 当前已确认的开票业务字段，只有以下内容：
8. 购买方名称
9. 购买方纳税人识别号
10. 销售方名称
11. 销售方纳税人识别号
12. 价税合计
13. 合计金额
14. 合计税额
15. 税率
16. 发票类型
17. 开票人

## 2. 现有表为什么不能直接复用

结合 `ExtendPlatform` 当前代码，以下现有表都不适合作为本需求主表：

### 2.1 `etcplus_merchant_invoice`

它本质上是商户开票资料表，不是开票执行记录表。

不适合原因：

1. 没有来源业务关联字段。
2. 没有 `FPQQLSH`。
3. 没有乐企返回票面字段和下载地址字段。
4. 没有状态机、失败原因、重试次数。

### 2.2 `etcplus_trans_invoice`

它本质上是停车交易发票结果表，来源对象是交易流水，不是服务费汇总记录或待开票记录。

不适合原因：

1. 关联对象错了。
2. 字段太少，只覆盖简单票面结果。
3. 不能支撑服务费开票的状态、重试、原报文、下载地址管理。

### 2.3 `TransferBill* / TransferBillTotal*`

这批对象属于旧的“申请-审核-登记发票号”流程。

不适合原因：

1. 强绑定旧审核流程。
2. 核心语义是申请单，不是乐企开票执行结果。
3. 没有 `FPQQLSH`、下载地址、原始报文等关键字段。

结论：

1. 本需求应新增独立的“服务费发票执行结果表”。
2. 如需保留重试过程留痕，再补一张“发票重试日志表”。
3. 不建议在旧表上打补丁式扩字段。

## 3. 推荐表设计

推荐最小可用设计如下：

1. 主表：`etcplus_service_fee_invoice`
2. 可选日志表：`etcplus_service_fee_invoice_retry_log`

其中主表是必须表；日志表用于增强重试留痕和联调排障，不是业务闭环必需。

## 4. 主表设计：`etcplus_service_fee_invoice`

### 4.1 表定位

一行代表一条待开票记录的开票执行结果。

说明：

1. 一条服务费汇总记录可能对应多张发票，这不是本表的问题。
2. 本表只认前一流程已经拆好并确认字段的待开票记录。
3. 一条待开票记录对应一条主发票记录。
4. 失败重试不新建主记录，仍落在同一条主记录上更新状态和重试次数。

### 4.2 主表只保留两类信息

#### 1. 开票业务字段快照

只保留需求已经确认要传给乐企的业务字段。

#### 2. 记录管理字段

只保留支撑状态、失败重试、票面回写、下载能力的运行字段。

原则：

1. 不追求“大而全”。
2. 不把未确认的购销方扩展资料一并塞入主表。
3. 不把审核、作废、红冲等非本期流程字段塞进主表。

以下字段在本期需求和当前传参确认表中没有明确要求，暂不纳入主表：

1. 购买方地址
2. 购买方电话
3. 购买方开户行
4. 购买方银行账号
5. 销售方地址
6. 销售方电话
7. 销售方开户行
8. 销售方银行账号
9. 发票摘要
10. 币种
11. 逻辑删除标记
12. 扩展 JSON 字段
13. 业务性质字段

### 4.4 关键约束建议

建议至少加以下约束：

1. 主键：`invoice_id`
2. 唯一键：`uk_fpqqlsh (fpqqlsh)`
3. 普通索引：`idx_merchant_status (merchant_id, invoice_status)`
4. 普通索引：`idx_service_fee_record_code (service_fee_record_code)`
5. 普通索引：`idx_source_record (source_record_id, source_record_type)`
6. 普通索引：`idx_invoice_no (invoice_no)`
7. 普通索引：`idx_create_at (create_at)`

说明：

1. `fpqqlsh` 必须唯一，这是整张表最关键的约束。
2. 不建议对 `service_fee_record_code` 加唯一约束，因为一条服务费汇总记录可能被前一流程拆成多条待开票记录。
3. 如果前一流程的 `source_record_id` 本身就是唯一待开票项，也可以对 `source_record_id + source_record_type` 增加唯一约束。

## 5. 可选日志表：`etcplus_service_fee_invoice_retry_log`

### 5.1 为什么建议加

主表可以支撑业务闭环，但如果完全不留重试日志，后续会丢掉这些信息：

1. 第几次重试发起的
2. 每次重试的请求时间和返回时间
3. 每次失败的原始返回码和返回消息
4. 是否真的使用了完全一致的原报文

因此如果你们后续要联调乐企、排查幂等和重复开票风险，建议加这张表。

### 5.2 推荐字段

| 字段名 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `retry_log_id` | bigint | 是 | 主键 |
| `invoice_id` | bigint | 是 | 对应主表ID |
| `fpqqlsh` | varchar(20) | 是 | 同一发票请求流水号 |
| `retry_no` | int | 是 | 第几次请求，从1开始 |
| `request_payload` | longtext | 是 | 当次发送报文 |
| `request_payload_hash` | varchar(64) | 是 | 当次报文摘要 |
| `request_at` | datetime | 是 | 请求时间 |
| `response_at` | datetime | 否 | 响应时间 |
| `return_code` | varchar(16) | 否 | 返回码 |
| `return_message` | varchar(1000) | 否 | 返回消息 |
| `invoice_status` | tinyint | 是 | 当次结果状态 |
| `operator_type` | tinyint | 是 | 触发方式：1系统首次发起、2人工重试、3系统补偿 |

| `create_at` | datetime | 是 | 创建时间 |

## 6. 字段设计取舍说明

### 6.1 为什么主表里保留购销方快照

因为本流程只消费前一流程给出的开票字段，后续商户资料表再变，也不能反向污染历史已开票记录。

所以：

1. 购买方名称、税号要做快照
2. 销售方名称、税号要做快照
3. 本期未确认的地址、电话、银行字段不强行入表

### 6.2 为什么保留 `request_payload`

因为乐企明确要求失败重试必须使用原流水号和原报文。

如果不存原报文：

1. 无法证明重试是否原样
2. 无法做联调排障
3. 无法复现超时和 `9999` 之类问题

### 6.3 为什么不建议本流程二次存“拆票逻辑字段”

因为拆票已经在前一流程结束，本流程只认结果。

所以不建议在本表里再设计：

1. 拆票规则字段
2. 拆票来源计算公式
3. 尾差分摊逻辑字段

这些都属于前一流程责任。

### 6.4 为什么金额字段用 `decimal(18,2)`

因为：

1. 需求文档已经按元、两位小数冻结展示和开票口径
2. 乐企接口金额字段也是元、两位小数
3. 本流程的表是开票结果表，不再承担内部结算分单位存储逻辑

## 7. 不建议加入主表的字段

以下字段不建议塞进主表：

1. 审核人、审核时间、复核人、复核意见
2. 拆票规则、拆票分摊公式
3. 红冲、作废、换票流程字段
4. 停车交易维度字段，如 `merchant_trans_id`
5. 与单次车牌交易发票直接绑定的旧字段
6. 未在当前开票字段确认表中的购销方扩展资料字段
7. 逻辑删除字段

原因很简单：这些都不是本期范围，塞进去会把新表重新污染成旧流程表。

## 8. 最终建议

如果你希望本期设计尽量稳、又不过度复杂，我的建议是：

1. 必建 `etcplus_service_fee_invoice`
2. 建议建 `etcplus_service_fee_invoice_retry_log`
3. 不复用 `etcplus_merchant_invoice`
4. 不复用 `etcplus_trans_invoice`
5. 不复用 `TransferBill*` 旧申请审核链路表

一句话总结：

这次应该建的是“服务费发票执行结果表”，而且是**精简版执行结果表**，不是“商户开票资料表”，也不是“停车交易发票表”，更不是“旧申请审核单表”。
