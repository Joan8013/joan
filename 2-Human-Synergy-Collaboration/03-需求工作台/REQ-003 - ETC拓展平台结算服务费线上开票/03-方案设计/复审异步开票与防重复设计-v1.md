## 1. 变更背景

| 问题 | 原因 | 目标 |
| --- | --- | --- |
| 财务复审点确认后页面「卡住」 | `financeFinalReview` 同步调用 `createInvoicesFromApply`，整段乐企外调阻塞 HTTP | 复审接口秒回 |
| 重复开票风险 | 并发复审、Job 重扫、页面重复提交 | 乐企 `issue` 每张票最多成功发起一次 |
| 流水号不稳定 | 旧逻辑 `RQ+时间戳` 生成，极端情况下可能重复建 row 产生新号 | 固定 `LHDF+16位数字`，与 `(applyId,splitSeq)` 绑定 |

## 2. 总体流程（修订后）

```text
商户提交开票申请
  → 运营审核 → 财务初审 → 财务复审（HTTP 仅改 audit_status=3，秒回）

Quartz Job（etcplus-job-report，每 2 分钟）
  jobReconBillInvoiceTask.issueApprovedApplies()
    → Feign → etcplus-system /reconBillInvoice/issueApprovedApplies
    → issueApprovedApplies(limit)
         扫描 audit_status=3 AND issue_start_at IS NULL
         CAS 认领 issue_start_at（每 apply 仅一次）
         逐 split 建 invoice（status=0）+ 行级 CAS 后调 GP_FPKJ 一次

Quartz Job（已有，每 1 分钟）
  jobReconBillInvoiceTask.queryPendingResult()
    → 仅 GP_FPCX 查询 invoice_status=1，不 issue

失败 / 超时（9992、9999 等）
  → Job 不自动重开
  → 商户在发票管理手工 retry（先 query，复用原 fpqqlsh + request_payload）
```

## 3. 财务复审解耦

### 3.1 接口行为

| 接口 | 修订前 | 修订后 |
| --- | --- | --- |
| `POST /reconBill/financeFinalReview` | 审核通过后同步 `createInvoicesFromApply` + 乐企 | **仅** `review()`：`audit_status` 2→3，写 audit_log |
| 响应时间 | 秒～分钟（取决于拆票数 × 乐企耗时） | 毫秒～百毫秒级 |

### 3.2 审核乐观锁

`updateInvoiceApplyIfAuditStatus`：`WHERE id=? AND audit_status=期望态`；影响行数 0 则「当前状态不允许审核」。防止并发双请求重复写审核态。

### 3.3 前端

管理端 `merchantReconBill`：财务复审通过成功提示「审核通过，系统将在后台自动开票」；列表看 **审核状态 + 开票状态** 变化，无需等待接口内完成开票。

## 4. Job 首轮开票（方案 B）

### 4.1 模块分层（与现有 queryPending 一致）

| 层级 | 模块 / 路径 |
| --- | --- |
| Quartz 入口 | `etcplus-job-report` → `JobReconBillInvoiceTask.issueApprovedApplies()` |
| Feign | `RemoteReconBillInvoiceService.issueApprovedApplies` |
| HTTP | `POST /reconBillInvoice/issueApprovedApplies` |
| 业务 | `ReconBillInvoiceServiceImpl.issueApprovedApplies(int limit)` |

### 4.2 Quartz 注册

脚本：`extend_platform/sql/recon_bill_invoice_issue_approved_job.sql`

| 字段 | 值 |
| --- | --- |
| `job_name` | 服务费复审通过自动开票 |
| `job_group` | `etcplus-job-report` |
| `invoke_target` | `jobReconBillInvoiceTask.issueApprovedApplies()` |
| `cron_expression` | `0 */2 * * * ?` |
| `concurrent` | `1`（禁止同 Job 并发） |

### 4.3 Job 内步骤（单 apply）

1. `selectApplyIdsPendingIssue(limit)`：`audit_status=3 AND issue_start_at IS NULL`
2. `claimApplyForIssue`：CAS 写 `issue_start_at`、`issue_status=1`；失败则 skip（已被其他实例认领）
3. 按拆票明细逐行：
   - `INSERT invoice`（`invoice_status=0`，`fpqqlsh=LHDF…`）；`uk_apply_split_seq` / `uk_detail_id` 冲突则 SELECT 已有行
   - `tryClaimInvoiceForIssue`：`WHERE invoice_status=0` 成功才调 `GP_FPKJ` **一次**
4. `syncApplyIssueStatus` 汇总 apply.`issue_status`
5. **无论成败，该 apply 不再进步骤 1**（`issue_start_at` 已设）

### 4.4 Job 明确不做

- 不对 `invoice_status=3` 自动 `retryIssue`
- 不替代 `queryPendingResult`（只查 `status=1`）

## 5. 乐企 FPQQLSH 规则（LHDF）

### 5.1 乐企规范摘要

- 20 位字母+数字；**一笔订单 / 一张发票 = 一个唯一流水号**
- 命名：**企业名称前四位缩写 + 十六位唯一字符串**
- 本公司缩写：**LHDF**（写死在代码 `ReconBillFpqqlshUtils.PREFIX`，不做配置项）
- 示例：`LHDF2020082910200001`（4+16=20）

### 5.2 代码生成规则（稳定、可预测）

```text
fpqqlsh = "LHDF" + String.format("%016d", applyId * 10L + splitSeq)
```

- `splitSeq`：1 或 2（拆票序号）
- **INSERT 时生成一次，写入 DB 后永不修改**
- 9992 / 9999 / 超时 retry：**必须**复用 DB 中已有 `fpqqlsh` 与 `request_payload`（与乐企文档一致）

实现类：`com.etcplus.system.business.invoice.util.ReconBillFpqqlshUtils`

### 5.3 存量数据

- 已用旧前缀 `RQ*` **且已调过乐企** 的记录：**禁止改号**
- 新票统一 `LHDF*`；未发起过的旧 `RQ*` 是否迁移由运维单独评估

## 6. 防重复开票四道闸

| 闸 | 机制 | 说明 |
| --- | --- | --- |
| ① 复审 API | 审核乐观锁 | 仅改 `audit_status`；重复点复审第二次被状态挡住 |
| ② apply 认领 | `issue_start_at` CAS | 每个 apply Job 只认领一次；`issue_start_at IS NULL` 才可扫入 |
| ③ 一行一票一号 | `uk_apply_split_seq`、`uk_detail_id`、`uk_fpqqlsh` + LHDF 稳定号 | 重复 INSERT 失败；同 logical 票同 fpqqlsh |
| ④ 行级 issue | `tryClaimInvoiceForIssue`（`invoice_status=0`） | 每张票 GP_FPKJ 只发一次；失败走商户 query+retry |

## 7. 失败与手工重开

| 入口 | 场景 | 行为 |
| --- | --- | --- |
| Job `issueApprovedApplies` | 复审通过后首轮 | 每 apply 一轮；失败不自动再 issue |
| Job `queryPendingResult` | `invoice_status=1` | 仅 GP_FPCX，不 issue |
| 商户 `POST .../reconBillInvoice/{id}/retry` | 失败/处理中 | 先 query；未开则复用 fpqqlsh |
| 商户 `POST .../apply/{applyId}/issue` | 批量补开 | `status=0`（Job 崩溃补跑）、`1`、`3`；仍走 CAS + 原号 |
| 管理 `createFromApply` | 运维补录 | 与 Job 同幂等逻辑；生产建议收紧权限 |

**原则：Job 只负责首轮 issue；失败由商户（或运维）手工重开，不自动重试。**
