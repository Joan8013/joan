# 方案设计 v4

需求：`REQ-003 ETC拓展平台结算服务费开票功能`

本文基于以下最新前提重写：

1. 一条服务费汇总记录可以开 1-2 张发票。
2. 商户先提交开票申请，业务及财务审核信息与申请信息在同一张表中。
3. 一张申请单对应 1-2 张发票执行记录。
4. 本期对接乐企开票接口和发票查询接口，查询只走定时补偿。
5. 下载同时开放 `PDF/OFD/XML`。

## 1. 方案目标

本期在 ExtendPlatform 中落一条完整的服务费发票执行链路：

1. 承接已审核通过的开票申请单。
2. 按申请单已冻结的拆票结果，生成 1-2 条单张发票执行记录。
3. 调用乐企开票接口。
4. 通过定时补偿调用乐企查询接口，补齐最终结果与下载地址。
5. 为商户提供发票记录查询、失败重试、成功下载能力。

## 2. 核心业务关系

### 2.1 上下游对象关系

本期对象关系应理解为：

1. 一条服务费汇总记录
2. 对应一张开票申请单
3. 一张申请单可拆成 1-2 张发票
4. 发票执行表按单张发票一条记录落库

映射关系：

1. `apply_id / apply_no` 对应申请单
2. `split_seq / split_total_count` 区分同一申请单下的第 1 张/第 2 张发票
3. `recon_bill_id / recon_bill_no` 负责回溯服务费汇总记录

### 2.2 审核信息处理

由于审核信息与申请信息放在同一张业务表中，因此：

1. 发票执行表不再单独关联审核单
2. 是否具备开票资格，以申请单自身审核通过状态为准

## 3. 代码现状判断

结合 `ExtendPlatform` 当前代码，仍有以下结论：

1. 商户端现有 `invoiceManage` 页面仍是占位页，需要整体替换为真实发票记录页
2. 旧 `TransferBill` 体系属于人工登记/审核历史链路，不适合承接本期乐企直连开票
3. 商户开票资料表只可作为购买方资料来源，不能承接发票执行结果
4. 当前未发现已落地的乐企开票和查询实现

结论：

本期仍需新增独立“服务费发票执行模块”。

## 4. 总体流程设计

### 4.1 开票触发时序

建议时序如下：

1. 商户提交开票申请
2. 申请表内完成业务/财务审核
3. 上游冻结该申请单的拆票结果
4. 上游调用本模块开票入口
5. 本模块按申请单拆分结果创建 1-2 条发票执行记录
6. 每条执行记录生成独立 `FPQQLSH`
7. 调用乐企开票接口
8. 同步成功则直接落结果
9. `CODE=1000` 或结果不完整时，交给定时补偿查询链路处理

### 4.2 为什么按申请单拆分

因为当前真实结构里没有 `apply_item_id`，所以本期不再设计“申请明细粒度”的输入模型。

本期最小执行粒度改为：

`申请单下的单张发票执行记录`

## 6. 后端对象设计

本期继续控制对象规模，不做过度拆分。

### 6.1 核心对象

1. `ReconBillInvoice`
   对应发票执行主表，一条记录代表一张发票执行明细。

### 6.2 入参/出参对象

   商户端返回对象。

### 6.3 服务与客户端

1. `ReconBillInvoiceService`
2. `ReconBillInvoiceMapper`
3. `ReconBillInvoiceRetryLogMapper`

## 7. 接口设计

### 7.1 上游开票入口

建议接口：

`POST /system/reconBillInvoice/createAndIssue`

入参至少包含：

1. `applyId`
2. `applyNo`
3. `reconBillId`
4. `reconBillNo`
5. `merchantId`
6. `merchantName`
7. `splitTotalCount`
8. 单张发票列表

其中单张发票列表中的每项至少包含：

1. `splitSeq`
2. `jshjAmount`
3. `hjjeAmount`
4. `hjseAmount`
5. `invoiceType`
6. 购销方信息
7. 项目明细
8. `remark`

### 7.2 商户端接口

1. `GET /system/mhApi/reconBillInvoice/list`
2. `POST /system/mhApi/reconBillInvoice/{id}/retry`
3. `GET /system/mhApi/reconBillInvoice/{id}/downloadOptions`

返回字段统一以后端正式模型为准，不沿用旧占位页字段名。

## 8. 乐企调用设计

### 8.1 开票接口

每条单张发票执行记录单独调用一次乐企开票接口：

1. 先落主记录
2. 生成 `FPQQLSH`
3. 固化请求报文
4. 发起开票

### 8.2 查询接口

本期查询接口只用于定时补偿：

1. 补齐 `CODE=1000` 的最终结果
2. 补齐下载地址
3. 校验最终票面信息

不设计人工触发查询入口。

补充冻结口径：

1. `quantity` 固定传 `1.000000`
2. `unit_price` 固定传 `3581.103773584905`
3. `remark` 由上游生成并满足乐企长度要求

## 9. 状态设计

### 9.1 发票执行表状态

仍保持 4 个：

1. 待开票
2. 开票中
3. 开票成功
4. 开票失败

### 9.2 申请单汇总状态

申请单自己的状态不放进发票执行表。

当前已确认：

1. 由上游负责汇总回写申请单状态
2. 本模块提供发票执行结果查询能力

可回写的申请单汇总状态例如：

1. 处理中
2. 部分成功
3. 全部成功
4. 全部失败

## 10. 重试设计

1. 仅失败记录允许重试
2. 最大 3 次
3. 重试复用原 `FPQQLSH`
4. 重试复用原报文
5. 重试不新增主记录

4. 失败时支持重试
5. 列表接口禁止返回 `request_payload` 与 `item_detail_payload`
6. 列表查询禁止 `SELECT *`

## 12. 实施顺序建议

1. 冻结申请单与发票执行表的关联口径
2. 落发票主表和重试日志表
3. 落开票入口、开票服务、乐企客户端
4. 落定时补偿查询任务
5. 落商户端查询、重试、下载接口
6. 改造商户端页面

## 13. 已冻结口径

1. 申请单汇总状态由上游负责回写。
2. `quantity` 固定传 `1.000000`，保留6位小数。
3. `unit_price` 固定传 `3581.103773584905`，保留15位小数。
4. `remark` 由上游生成并满足乐企长度要求，本模块透传。

## 14. 结论

1. 本期真实模型应从“申请明细驱动”收敛为“申请单驱动 + 单张发票执行明细”。
2. `apply_id` 应作为内部强关联键保留，`apply_no` 作为业务追踪键保留。
3. `split_seq` 是这版设计里最关键的新增字段之一。
4. 这版方案已经和你最新截图及反馈口径对齐。
5. 当前已可作为进入开发前的最终设计基线。
