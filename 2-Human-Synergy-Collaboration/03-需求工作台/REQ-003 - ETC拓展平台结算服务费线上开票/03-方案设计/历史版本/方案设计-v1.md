# 方案设计 v1

需求：`REQ-003 ETC拓展平台结算服务费开票功能`

本文基于以下内容输出：

1. `01-需求澄清/需求澄清-v2.md`
2. `02-影响分析/影响分析-v1.md`
3. `ExtendPlatform` 现有代码结构
4. 乐企开票接口文档 `GP_FPKJ` 及相关查询接口

本文目标是给出可落地的前后端方案，不只停留在表设计。

## 1. 方案目标

本期要在 ExtendPlatform 中补齐一条完整链路：

1. 接收前一流程已生成好的待开票数据。
2. 调用乐企 `GP_FPKJ` 发起服务费开票。
3. 保存开票状态、票面结果、下载地址和失败原因。
4. 为商户前台提供发票记录查询、失败重试、成功下载能力。

本期明确不做：

1. 审核流
2. 拆票规则生成
3. 红冲、作废、换票
4. 商户在线修改开票报文内容

## 2. 现状判断

结合代码现状，当前系统里有三类“接近但不能直接拿来用”的能力：

### 2.1 商户开票资料能力

已有：

1. `mhApi/invoice` 商户开票资料查询
2. `etcplus_merchant_invoice` 等商户开票资料表

定位：

1. 这是商户抬头资料，不是发票执行记录。
2. 可以作为购买方资料来源参考，但不能承接本期主流程。

### 2.2 交易发票能力

已有：

1. `etcplus_trans_invoice`
2. 交易发票查询 Mapper：`EtcplusTransInvoiceMapper.xml`

定位：

1. 这是停车交易开票结果表。
2. 核心关联字段是 `merchant_trans_id`。
3. 不适合服务费汇总开票。

### 2.3 旧的申请/审核/登记发票号能力

已有：

1. `TransferBillController`
2. `TransferBillTotal* / TransferBill* / TransferBillN*`

定位：

1. 这是旧的“申请单 + 审核 + 手工登记票号”链路。
2. 与本期“前一流程已定内容，系统直连乐企开票”不匹配。

结论：

1. 本期应新增独立的“服务费开票模块”。
2. 商户前端页面可以沿用现有 merchant UI 风格和目录结构。
3. 后端不能继续挂靠旧 `TransferBill*` 流程。

## 3. 总体方案

### 3.1 方案思路

总体采用“前一流程产出待开票记录 + 本模块负责开票执行和结果管理”的结构：

1. 前一流程负责生成待开票记录，并冻结开票字段。
2. 本模块按待开票记录发起乐企开票。
3. 本模块维护服务费发票主记录表。
4. 本模块向商户前台提供查询、重试、下载接口。

### 3.2 逻辑边界

前一流程负责：

1. 拆票
2. 发票类型确定
3. `JSHJ/HJJE/HJSE` 金额冻结
4. `COMMON_FPKJ_XMXX` 项目明细生成
5. 判定“哪些待开票记录可以进入开票”

本流程负责：

1. 生成 `FPQQLSH`
2. 组装并保存乐企开票报文
3. 调用乐企接口
4. 维护状态机
5. 处理失败重试
6. 保存下载地址并提供下载

## 4. 后端方案

### 4.1 模块落位建议

建议在 `etcplus-modules/etcplus-system` 下新增独立业务包，按现有 merchant split 风格组织：

1. 商户前台 Controller：
2. `com.etcplus.system.split.merchant.invoice.controller`
3. 后端管理端 Controller：
4. `com.etcplus.system.manage.invoice.controller`
5. 业务 Service：
6. `com.etcplus.system.business.invoice.service`
7. Domain / Mapper：
8. `com.etcplus.system.business.invoice.domain`
9. `com.etcplus.system.business.invoice.mapper`

这样做的原因：

1. 与现有 `split.merchant` 和 `manage` 双端结构一致。
2. 不污染旧 `settle` 和 `trans` 业务包。
3. 方便后续扩展红冲、作废等发票能力。

### 4.2 核心后端对象

上一版对象拆分偏细，这一版按当前需求规模收敛为“够用且清晰”的最小集合。

建议优先新增以下对象：

1. `ServiceFeeInvoice`
2. `ServiceFeeInvoiceRetryLog`
3. `ServiceFeeInvoiceQueryReq`
4. `ServiceFeeInvoiceVO`
5. `ServiceFeeInvoiceService`
6. `ServiceFeeInvoiceMapper`
7. `ServiceFeeInvoiceRetryLogMapper`
8. `LeqInvoiceClient`

各对象职责如下：

1. `ServiceFeeInvoice`
   作用：发票主实体，对应主表 `etcplus_service_fee_invoice`，承载开票结果、购销方快照、金额快照、幂等字段和下载地址等核心数据。
2. `ServiceFeeInvoiceRetryLog`
   作用：重试日志实体，对应重试日志表，保存每次请求的时间、报文、返回码和结果状态。
3. `ServiceFeeInvoiceQueryReq`
   作用：商户前台发票记录列表查询入参，承接查询条件，不直接复用实体做查询对象。
4. `ServiceFeeInvoiceVO`
   作用：商户前台列表和详情返回对象，字段命名按正式发票数据模型输出，不直接暴露数据库实体。
5. `ServiceFeeInvoiceService`
   作用：业务主服务，负责创建发票记录、发起开票、查询列表、失败重试、下载地址处理和状态回写。
6. `ServiceFeeInvoiceMapper`
   作用：发票主表数据库访问层。
7. `ServiceFeeInvoiceRetryLogMapper`
   作用：发票重试日志表数据库访问层；如果最终不单独建日志表，可取消。
8. `LeqInvoiceClient`
   作用：封装乐企接口调用，包括开票、状态查询、下载地址查询等第三方交互。

当前不建议一开始就拆出的对象：

1. `LeqInvoiceRequestBuilder`
2. `ServiceFeeInvoiceAsyncService`
3. `ServiceFeeInvoiceDownloadReq`

原因：

1. 当前需求规模下，过早细拆会让方案显得复杂但收益不大。
2. 若后续轮询、回调、报文组装复杂度上升，再从 `ServiceFeeInvoiceService` 中继续拆分会更自然。

### 4.3 数据模型

本期建议采用两张表：

1. 主表：`etcplus_service_fee_invoice`
2. 日志表：`etcplus_service_fee_invoice_retry_log`

详细字段设计见：

[发票表设计-v1.md](E:\\CodexSpace\ETC-AI-ReqFlow-Structured\03-需求工作台\REQ-003%20-%20ETC拓展平台结算服务费开票功能\03-方案设计\发票表设计-v1.md)

本方案不建议复用：

1. `etcplus_merchant_invoice`
2. `etcplus_trans_invoice`
3. `TransferBill*`

### 4.4 关键字段来源

#### 来源业务字段

来源建议：

1. 待开票记录主键：前一流程输出
2. 服务费汇总记录编码：前一流程输出
3. 商户号、商户名称：前一流程输出，必要时与结算明细补查校验
4. 业务性质：前一流程输出，必要时可参考 `MhEtcplusSettleDetail.bizNature`

#### 购买方字段

优先来源：

1. 前一流程待开票记录中的已冻结购买方字段

参考来源：

1. `MhMerchantInvoice`
2. `MhMerchantEnterprise.invoiceTaxNumber`

原则：

1. 历史开票必须保存快照，不能运行时总去查资料表覆盖。

#### 销售方字段

来源：

1. 平台统一配置

建议：

1. 通过配置中心或系统参数维护
2. 发起开票时写入主表快照

#### 金额字段

来源：

1. 前一流程冻结好的 `JSHJ/HJJE/HJSE`

原则：

1. 本流程不做二次计算
2. 只做合法性校验和直接落库

### 4.5 状态机设计

主状态使用 4 个状态：

1. `0-待开票`
2. `1-开票中`
3. `2-开票成功`
4. `3-开票失败`

状态流转：

1. 前一流程写入待开票记录后，本模块创建主记录，状态为 `待开票`
2. 发起 `GP_FPKJ` 前更新为 `开票中`
3. 若同步返回 `CODE=0000`，更新为 `开票成功`
4. 若同步返回 `CODE=1000`，保留 `开票中`，等待异步结果
5. 若返回其他错误码，更新为 `开票失败`
6. 用户点击“重试”后，再次进入 `开票中`

### 4.6 幂等与重试设计

#### 幂等主键

使用：

1. `FPQQLSH`

规则：

1. 固定 20 位
2. 全局唯一
3. 同一条发票主记录只生成一次
4. 后续重试必须复用原值

#### 重试规则

1. 仅 `开票失败` 允许重试
2. 最大重试次数为 3
3. 重试时复用：
4. 原 `FPQQLSH`
5. 原 `request_payload`
6. 原 `item_detail_payload`
7. 不允许改金额、类型、抬头、明细

#### 并发控制

建议：

1. 重试前校验状态必须是 `开票失败`
2. 更新状态时带条件更新，例如 `where invoice_status = 3`
3. 同时更新 `retry_count`
4. 若条件更新失败，说明已被其他线程处理，直接返回“请刷新后重试”

### 4.7 乐企接口调用设计

#### 核心接口

必须对接：

1. `GP_FPKJ`

建议预留：

1. 发票下载地址查询接口
2. 发票状态查询接口

#### 同步返回处理

1. `CODE=0000`
2. 解析票面字段、地址字段，主表改成功
3. `CODE=1000`
4. 记录 `LSH`，主表保留开票中
5. 其他错误码
6. 主表改失败，写 `return_code / return_message / fail_reason`

### 4.8 异步结果处理

现阶段建议优先采用“状态查询任务轮询”方案，而不是强依赖回调。

原因：

1. 现有代码里还没有明显成型的乐企开票回调链路
2. 轮询对本期落地更可控

建议实现：

1. 新增定时任务或轻量 job
2. 扫描 `invoice_status = 1` 的开票中记录
3. 对有 `LSH` 或有 `FPQQLSH` 的记录调用状态查询
4. 查到终态后回写成功或失败

说明：

1. 如果后续代码核对发现已有稳定回调基础设施，可以把异步方案替换成回调优先
2. 但本版设计先按“轮询可落地”输出

### 4.9 下载设计

下载策略：

1. 优先 `PDF_URL`
2. 若 `PDF_URL` 为空，则使用 `OFD_URL`
3. `XML_URL` 不作为商户前台默认展示入口

后端接口建议返回：

1. `downloadType`
2. `downloadUrl`

是否代理下载：

1. 若乐企返回地址可直接访问，前端可直接跳转下载
2. 若存在签名、鉴权或跨域问题，后端再补代理下载接口

本期建议：

1. 先按“返回下载地址给前端”设计
2. 代理下载作为兼容预案，不抢先实现

## 5. 后端接口设计

### 5.1 商户前台接口

建议新增以下接口：

#### 1. 查询发票记录列表

`GET /system/mhApi/serviceFeeInvoice/list`

查询条件：

1. 开票申请时间范围
2. 服务费汇总记录编码
3. 发票号码
4. 开票状态

返回字段：

1. `invoiceId`
2. `serviceFeeRecordCode`
3. `merchantName`
4. `bizNature`
5. `invoiceType`
6. `buyerName`
7. `buyerTaxNo`
8. `invoiceNo`
9. `invoiceCode`
10. `jshjAmount`
11. `invoiceStatus`
12. `failReason`
13. `invoiceDate`
14. `retryCount`
15. `canRetry`
16. `canDownload`

字段命名原则：

1. 前端接口返回字段统一以后端正式发票数据模型为准。
2. 不以当前页面临时占位字段名为准。
3. 页面应适配后端正式字段，不允许后端为了兼容旧页面占位命名而继续输出混杂字段。

例如：

1. 用 `serviceFeeRecordCode`，不继续混用 `reconBillNo`
2. 用 `invoiceStatus`，不继续混用 `itemStatus`
3. 用 `buyerName`、`buyerTaxNo`，不继续混用 `invoiceTitle`、`taxpayerNo`
4. 用 `failReason`，不继续混用 `failureReason`

#### 2. 失败重试

`POST /system/mhApi/serviceFeeInvoice/{invoiceId}/retry`

行为：

1. 校验当前登录商户是否有权操作
2. 校验状态必须是失败
3. 校验重试次数未超限
4. 复用原 `FPQQLSH` 和原报文重发

#### 3. 下载发票

`GET /system/mhApi/serviceFeeInvoice/{invoiceId}/download`

行为：

1. 校验当前登录商户是否有权访问
2. 校验状态必须是成功
3. 返回下载地址或下载结果对象

### 5.2 管理端接口

本期可选。

如果纳入，建议新增：

1. `GET /system/serviceFeeInvoice/list`
2. `GET /system/serviceFeeInvoice/{invoiceId}`

只做查询，不做审核。

## 8. 异常与边界处理

### 8.1 失败分类

失败至少分三类保存：

1. 同步失败
2. 异步终态失败
3. 超时未确认

### 8.2 特殊错误码

重点关注：

1. `9992`
2. `9999`
3. 超时
4. `8009`

处理原则：

1. 不改 `FPQQLSH`
2. 不改报文
3. 只允许原样重试

### 8.3 数据一致性

必须保证：

1. 发票主记录创建成功后才能发起开票
2. 调用前先落原始报文
3. 成功后回写票面字段
4. 失败后保留错误码和错误消息

## 9. 实施顺序建议

建议按以下顺序开发：

1. 后端表结构落库
2. 后端 Domain / Mapper / Service / Controller
3. 乐企调用封装与重试逻辑
4. 商户前台列表页改造
5. 下载与重试交互
6. 异步查询任务
7. 联调与验收

## 10. 方案结论

1. 本期应新增独立“服务费开票模块”，不能继续挂靠旧申请审核或交易发票链路。
2. 后端核心是两张表、一条乐企开票链路、一个商户前台查询/重试/下载接口组、以及一个异步结果处理机制。
3. 前端核心是把现有 merchant 端 `invoiceManage` 页面从“占位壳子”改造成真正的发票记录管理页，并切换到独立发票接口。
4. 本方案已经覆盖前后端、接口、状态、异常和数据设计，具备进入任务拆分的基础。
