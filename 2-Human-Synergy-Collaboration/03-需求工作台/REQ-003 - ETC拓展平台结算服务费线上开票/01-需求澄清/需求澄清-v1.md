当前建议按以下顺序理解原始材料：

1. `平台结算服务费开票功能.md` 作为主需求文档，定义业务背景、页面字段、权限和主流程。

## 2. 需求背景

当前平台会向停车场商户收取结算服务费，但发票申请和开具过程缺少系统化闭环，容易产生以下问题：

1. 商户申请开票依赖线下沟通，效率低。
2. 发票状态、失败原因、下载入口缺少统一查询位置。
3. 乐企开票能力与平台业务流程未打通，无法形成申请、审核、开票、回写、查询的完整链路。

本需求目标是在 ETC 拓展平台中建立“商户申请 -> 平台审核 -> 乐企开票 -> 结果回写 -> 商户查询下载”的线上开票闭环。

## 3. 本期初步范围

结合当前主需求文档，当前本期范围建议包括：

1. 商户选择“已结算”的服务费汇总单据发起开票申请。
2. 系统自动带出购买方信息，包括商户企业名称和纳税人识别号，且商户不可修改。
3. 单张服务汇总单据支持拆分成多张发票，但拆分后的价税合计总和必须等于原单总金额。
4. 平台审核通过后，系统调用乐企接口开票。
5. 开票成功后回写发票代码、发票号码、开票日期、下载地址等结果信息。
6. 提供发票列表页，支持商户端查询和下载已开发票。
7. 支持开票失败后的重新开票，并限制同一张发票最多重试 3 次。
8. 平台端支持按商户维度查看全部发票，商户端仅查看自己名下发票。
9. 商户可自行选择发票类型为数电专票或数电普票。
10. 当商户选择专票时，需要校验该商户已被标记为一般纳税人。

说明：

1. 主文档中“服务汇总编号（关联对账单）”表述说明页面主对象更接近服务费汇总单据，而不是单笔交易。
2. 当前文档未明确该单据在系统中的正式名称，后续建议统一命名后再进入设计。

## 4. 本期初步非范围

根据当前材料，以下内容不应默认纳入本期：

1. 红冲、作废、换票等逆向发票流程。
2. 商户修改购买方信息后重新开票的能力。
3. 发票抬头、税号在线编辑能力。
4. 发票 PDF 模板定制能力。
5. 除“重新开票”外的复杂失败补偿策略可视化能力。
6. 财务结算、对账口径本身的重构。
7. 非结算服务费类业务的一并开票。

## 5. 角色与职责

| 角色 | 当前职责理解 |
| --- | --- |
| 商户 | 选择可开票单据、发起申请、选择发票类型、查看结果、下载发票 |
| 平台审核角色 | 审核商户开票申请，决定是否进入实际开票 |
| 财务 | 维护销售方固定开票信息，参与审核规则确认，处理异常兜底 |

说明：

1. 当前材料只写了“平台审核后开具发票”，未明确审核角色到底是财务、运营，还是二者之一。
2. “销售方名称、税号由财务统一配置，固定不变”已是当前明确规则。

## 6. 主流程澄清

### 6.1 主流程骨架

根据当前材料，主流程当前理解如下：

1. 商户选择已结算的服务费汇总单据，发起开票申请。
2. 系统自动带出购买方信息，商户仅选择发票类型，不修改名称和税号。
3. 如单据需要拆票，商户录入多张发票的拆分金额，系统校验总额一致。
4. 平台审核通过后，系统调用乐企接口发起开票。
5. 开票成功后，系统回写票面结果信息并提供下载入口。
6. 如开票失败，记录失败原因，并允许在限制次数内重新开票。

### 6.2 当前可明确的状态

页面字段中已明确以下发票状态：

1. `待开票`
2. `开票中`
3. `已开票`
4. `开票失败`

当前理解：

1. 商户申请提交且尚未通过平台审核前，是否直接记为 `待开票`，材料未说清。
2. “平台审核”本身是否需要单独状态，例如 `待审核`，材料未说清。
3. “已开票”应指单张发票记录开票成功，而不是整张服务汇总单所有拆票都已成功，这一点仍需确认。

### 6.3 拆票流程

当前可以确定的规则：

1. 同一张服务汇总单据可拆成多张发票。
2. 各张发票的价税合计之和必须等于原单总金额。
3. 拆分后每张发票都应有独立的开票结果和重试计数。

当前未明确的点：

1. 是先按商户手工拆分，还是系统给默认拆分方案。
2. 拆票后平台审核是审核整单，还是审核拆分后的每张发票。
3. 部分发票成功、部分失败时，汇总单主状态如何展示。

## 7. 关键口径澄清

### 7.1 开票对象口径

| 项目 | 当前理解 |
| --- | --- |
| 销售方名称 | 平台固定配置 |
| 销售方税号 | 平台固定配置 |
| 购买方名称 | 商户企业名称，系统自动带入，不可修改 |
| 购买方税号 | 商户纳税人识别号，系统自动带入，不可修改 |
| 发票类型 | 商户选择数电专票或数电普票 |
| 专票资格 | 商户需为一般纳税人 |

### 7.2 金额口径

| 项目 | 当前理解 |
| --- | --- |
| 价税合计 | 以单张发票申请金额为准 |
| 不含税金额 | 按 `价税合计 / 1.06` 计算 |
| 税额 | 按 `价税合计 - 不含税金额` 计算 |
| 税率 | 当前按 6% 理解 |

当前风险：

1. 主文档给出了计算公式，但没有说明保留小数位数、四舍五入规则、尾差归属规则。
2. 原始金额单位未明确是“元”还是“分”，后续必须在设计前冻结。

### 7.3 状态与审核口径

当前可明确：

1. 存在“平台审核通过后才开票”的前置条件。
2. 开票结果至少区分成功和失败。
3. 失败后支持重试，且最多 3 次。

当前未明确：

1. 平台审核是一层还是多层。
2. 审核不通过后的状态、提示、是否允许修改后重新提交。
3. `待开票` 是审核前状态还是审核后待调用状态。

### 7.4 幂等与重试口径

当前可明确：

1. 开票失败支持重新开票。
2. 同一张发票最多允许重试 3 次。

当前必须挂起确认：

1. “同一张发票”是指单条拆票记录，还是整张服务汇总单。
2. 网络超时场景下，若乐企实际已成功但平台未收到响应，如何避免重复开票。
3. 重试是否允许人工触发，还是系统自动触发。

### 7.5 权限与数据范围口径

当前可明确：

1. 商户端仅能查看自己名下发票。
2. 平台端财务/运营可查看全部商户发票。

当前未明确：

1. 平台端是否区分“仅查看”和“可审核/可重试/可下载”不同权限。
2. 商户端是否能看到尚未成功开票的失败记录和失败原因。

## 10. 澄清阶段结论

1. 需求主线已经清楚，本质是一个围绕结算服务费的线上开票闭环需求。
2. 当前已能确定的核心规则包括：购买方信息不可改、支持拆票、平台审核后开票、失败可重试、重试上限 3 次、商户和平台权限隔离、专票需一般纳税人资格。
3. 当前最大风险集中在四类口径：可开票单据准入、审核状态机、金额计算规则、失败重试与幂等。
4. 由于本需求涉及金额、状态和跨系统开票一致性，建议继续按 `A 类需求` 推进。
5. 在 Q-001 到 Q-010 未冻结前，不建议直接进入正式开发。
