# 影响分析起点 v1

需求：REQ-DEMO-001 助缴成功率和成本统计报表

本文只作为影响分析起点，用于指导后续代码阅读和方案设计。由于关键业务口径尚未确认，本文不直接转化为开发任务。

## 1. 初步影响范围

| 范围 | 当前判断 | 说明 |
| --- | --- | --- |
| 运营后台菜单/页面 | 有影响 | 需要新增报表模块和查询页面 |
| 后端查询接口 | 有影响 | 需要按商户、时间范围返回统计列表和合计 |
| 数据库查询 | 有影响 | 涉及多表关联、分组、去重、金额汇总 |
| 权限配置 | 可能有影响 | 新菜单是否需要角色权限待确认 |
| 导出能力 | 未确认 | 原始材料未提，不默认纳入 |
| 定时任务 | 暂无明确影响 | 当前看是实时查询报表 |
| 资金主链路 | 暂无直接影响 | 只统计展示，不改变扣款、清分、结算 |

## 2. 初步涉及数据表

| 表 | 用途草案 | 待核对点 |
| --- | --- | --- |
| `etcplus_merchant` | 根据商户编号查询商户名称 | 商户筛选来源和商户范围 |
| `ep_ap_order` | 统计上传日期、平台接收流水、车牌、已补缴订单、补缴金额；现有报表按 `status = 2` 判定已补缴/已缴费 | 车牌颜色字段、金额单位、是否需同时校验 `pay_status = 2` |
| `ep_ap_inf_req` | 识别上传流水请求，`biz_method = assist.order.upload.req` | 与订单或响应表的关联键 |
| `ep_ap_inf_res` | 判断平台是否接收，`code != 9999` | `code=9999` 的业务语义 |
| `ep_ap_sms_notify` | 统计发送成功短信数量，`status = 2` | 商户流水号关联方式 |
| `etcplus_trans` | 用 `ep_ap_order.merchant_order_id` 关联 `merchant_trans_id`，统计 `merchant_fee_0` 收益 | 退款影响和一对多/多对一关联情况 |

## 3. 初步查询维度

| 维度 | 当前理解 | 待确认点 |
| --- | --- | --- |
| 商户 | 支持全部商户和单商户，只展示助缴业务商户 | 助缴业务商户识别条件需代码核对 |
| 日期 | 默认当天是页面默认值，支持单日和日期区间 | 日期字段来源需代码核对 |
| 分组 | 商户 + 上传日期，日期区间按天拆行 | 正常场景一个商户一天内上传一批助缴流水 |
| 合计 | 页面底部展示合计，成功率以现有报表实现为准，按 `合计已补缴流水数 / 合计发送短信数量` 加权计算 | 分母为 0 时展示口径待确认 |

## 4. 重点技术风险

| 编号 | 风险 | 影响 | 建议处理 |
| --- | --- | --- | --- |
| RISK-001 | 需求口径曾误写为 `payment_status`，但代码中实际字段为 `status` 和 `pay_status` | 若沿用错误字段名，会导致设计和开发偏离现有模型 | 已核对：现有报表按 `ep_ap_order.status = 2` 统计 |
| RISK-002 | 助缴业务商户识别条件未核对 | 商户下拉可能混入非助缴商户或漏商户 | 代码核对商户来源和业务标识 |
| RISK-003 | 多表关联键未明确 | 统计数量和金额可能错漏 | 代码阅读时优先核对关联字段 |
| RISK-004 | 车牌去重口径涉及车牌颜色 | 车牌数量和已补缴车牌数可能失真 | 确认车牌颜色字段和空值处理 |
| RISK-005 | 金额单位存在分/元转换 | 短信成本和补缴金额展示可能错误 | 明确数据库单位和页面单位 |
| RISK-006 | 分母为 0 时成功率展示口径未确认 | 页面可能出现除零、空值或误导性 0%/100% | 产品确认空值展示规则 |
| RISK-007 | 退款或撤销订单影响未说明 | 已补缴金额和收益可能偏高 | 确认是否扣除退款/冲正 |

## 5. 后续代码阅读方向

后续进入代码核对时，建议按以下方向查找：

1. 运营后台现有报表模块的菜单、权限、路由和页面模式。
2. 助缴相关订单表 `ep_ap_order` 的实体、Mapper、状态枚举和金额字段。
3. 接口流水表 `ep_ap_inf_req`、`ep_ap_inf_res` 的关联关系。
4. 短信通知表 `ep_ap_sms_notify` 的发送状态和关联字段。
5. 交易流水表 `etcplus_trans` 中 `merchant_trans_id`、`merchant_fee_0` 的含义。
6. 现有报表接口是否已有分页、合计、导出、权限复用模式。

## 6. 当前影响分析结论

1. 该需求适合作为最小试跑，因为它比纯 UI 复杂，但不直接改资金主链路。
2. 字段口径和核心公式已经基本确认；成功率以现有报表实现为准，已补缴/已缴费按 `ep_ap_order.status = 2` 判定。
3. 当前仍不建议直接进入开发任务拆分，原因是关联键、金额单位、助缴业务商户识别条件、分母为 0 的展示规则和退款影响还需要代码核对或业务确认。
