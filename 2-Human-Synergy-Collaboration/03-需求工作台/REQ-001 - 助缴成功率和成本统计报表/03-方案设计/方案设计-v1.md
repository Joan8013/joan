# 方案设计 v1

需求：REQ-DEMO-001 助缴成功率和成本统计报表

本文用于最小试跑。由于该需求已完成，本文不是重新设计，而是基于现有实现回放“方案设计阶段应该沉淀什么”。

## 1. 方案目标

在运营后台提供“助缴成功率及成本统计报表”，按商户和上传日期查询助缴业务上传、接收、短信、补缴、成本、收益等统计数据，并提供合计行和导出能力。

## 2. 总体实现路径

| 层级 | 现有实现 | 说明 |
| --- | --- | --- |
| 前端页面 | `etcplus-ui-manage/src/views/form/apSuccessCostReport/index.vue` | 查询、重置、导出、列表展示、金额和成功率格式化 |
| 后端接口 | `EpApSuccessCostReportController` | `/epApSuccessCostReport/list` 查询，`/epApSuccessCostReport/export` 导出 |
| 查询服务 | `EpApSuccessCostReportServiceImpl` | 查询明细和合计，合计行补默认值 |
| 查询 Mapper | `system/assistPay/form/EpApSuccessCostReportMapper.xml` | 从报表结果表分页查询和汇总 |
| 报表生成任务 | `JobEpApSuccessCostReportTask` | 每日重建和按条件重建报表结果 |
| 生成 Mapper | `job/EpApSuccessCostReportMapper.xml` | 从原始业务表聚合写入 `ep_ap_success_cost_report` |
| 表结构脚本 | `sql/testhtjf/assist_pay_success_cost_report.sql` | 报表表、菜单、权限、定时任务初始化 |

## 3. 数据流

1. 原始助缴上传、订单、短信、交易流水进入业务表。
2. 定时任务按上传日期或订单更新时间重建报表。
3. 聚合结果写入 `ep_ap_success_cost_report`。
4. 运营后台查询接口从结果表读取明细和合计。
5. 前端展示金额、百分比，并支持导出。

## 4. 核心口径

| 指标 | 现有实现口径 |
| --- | --- |
| 总上传流水数量 | `ep_ap_inf_req.biz_method = 'assist.order.upload.req'`，并排除 `ep_ap_inf_res.code = '9999'` |
| 平台接收流水数量 | `ep_ap_order` 按商户和 `create_at` 日期计数 |
| 发送短信数量 | `ep_ap_sms_notify.status = 2` 且按 `order_number` 关联订单 |
| 短信成本 | 发送短信数量 * 3 分，即 0.03 元/条 |
| 车牌数量 | 平台接收订单按 `plate_number + plate_color` 去重 |
| 已补缴总车牌数 | `ep_ap_order.status = 2` 后按 `plate_number + plate_color` 去重 |
| 已补缴流水数 | `ep_ap_order.status = 2` 的订单数 |
| 总成功率 | `已补缴流水数 / 发送短信数量` |
| 已补缴总金额 | `ep_ap_order.status = 2` 的 `parking_fee` 汇总 |
| 总收益 | `ep_ap_order.order_number = etcplus_trans.merchant_trans_id` 后汇总 `merchant_fee_0` |

## 5. 实现回放发现的偏差

| 偏差 | 当前代码现状 | 处理建议 |
| --- | --- | --- |
| 商户筛选 | 前端是商户编号、商户名称输入框，不是下拉框 | 作为已完成需求偏差记录；如果产品坚持下拉，另起变更 |
| 默认日期 | 前端默认昨天，不是当天 | 结合定时任务每日跑昨日数据看是合理实现；需求文档需补充解释 |
| 导出能力 | 前端和后端已实现导出 | 说明实际交付范围大于原始材料，不应再标为未确认 |
| 成功率分母 | 现有实现使用短信数/追缴流水数口径，不使用车牌数量 | 已按用户确认，以现有报表为准 |

## 6. 方案边界

1. 本报表是运营报表，不作为财务对账和结算依据。
2. 本需求不改资金主链路、清分、结算、划账逻辑。
3. 已完成需求回放时，不建议倒推改代码；应记录实现和需求文档之间的差异。
