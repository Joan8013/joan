# 需求澄清 v1

需求：REQ-DEMO-001 助缴成功率和成本统计报表

本文基于 `00-原始材料` 中的 Word 需求说明和 Excel 字段取数逻辑整理。当前阶段只做澄清，不进入方案设计和开发任务拆分。

## 1. 需求背景

运营侧需要在 ETC 拓展系统运营后台新增“助缴成功率及成本统计报表”，用于实时监控助缴业务的成本、补缴效率和收益情况。

## 2. 初步范围

本期初步范围：

1. 新增运营后台报表模块。
2. 支持按商户筛选。
3. 支持按单日或日期区间筛选。
4. 展示助缴上传、平台接收、短信发送、短信成本、车牌、补缴、成功率、金额、收益等统计指标。
5. 支持查询和重置操作。

## 3. 初步非范围

以下内容原始材料未明确，不应默认纳入本期：

1. 报表导出。
2. 定时生成日报、月报。
3. 图表看板。
4. 商户端查看。
5. 财务结算或对账确认流程。
6. 短信成本配置后台。

如以上能力需要纳入，必须由产品或业务单独确认。

## 4. 查询条件

| 控件 | 类型 | 当前理解 | 待确认点 |
| --- | --- | --- | --- |
| 商户选择 | 下拉框 | 默认全部商户，选项只展示助缴业务商户，后续新增助缴业务商户需自动同步 | 助缴业务商户的识别条件需代码核对 |
| 时间范围 | 日期选择器 | 支持单日和日期区间，默认当天是页面默认值；日期区间按天拆行 | 日期筛选字段来源仍需代码核对 |

| 重置按钮 | 操作按钮 | 恢复默认筛选项 | 重置后是否自动查询 |

## 5. 报表字段初步口径

当前已确认报表字段以 Excel 字段取数逻辑为准。

| 字段 | 已确认/当前口径 | 待确认点 |
| --- | --- | --- |
| 商户名称 | 根据商户编号关联 `etcplus_merchant` | 商户编号来源字段待确认 |
| 上传日期 | 日期筛选默认当天，日期区间按天拆行 | 日期字段来源需代码核对 |
| 总上传流水数量 | `ep_ap_inf_req.biz_method = assist.order.upload.req` 对应上传流水 | 与响应表关联方式待确认 |
| 平台接收流水数量 | 已确认等同审核合格流水数量，即已审核合格的流水 | 具体审核合格状态字段需代码核对 |
| 审核合格流水数量 | 已确认与平台接收流水数量为同一指标 | 页面字段以 Excel 为准，不单独按 Word 字段扩展 |
| 发送短信数量 | 按商户流水号匹配 `ep_ap_sms_notify.status = 2` | 短信发送成功状态是否固定为 2 |
| 短信成本（元） | 成功短信数 * 0.03 元 | 已确认固定 0.03 元/条 |
| 车牌数量 | 审核合格流水中按车牌+颜色去重 | 车牌颜色字段来源待确认 |
| 已补缴总车牌数 | 现有报表按 `ep_ap_order.status = 2` 判定已补缴/已缴费订单，按车牌号+颜色去重；一个车牌只要有一笔已补缴订单即计入 | 是否需要同时校验 `pay_status = 2` 待评审确认 |
| 总成功率 | 以现有报表实现为准：`已补缴流水数 / 发送短信数量`；合计行采用加权计算，即 `合计已补缴流水数 / 合计发送短信数量` | 分母为 0 时页面展示口径待确认 |
| 已补缴总金额 | 平台接收流水中已补缴订单的 `total_amount` 求和 | 金额单位和退款影响待确认 |
| 总收益 | 取平台接收流水中已补缴订单，用 `ep_ap_order.merchant_order_id` 关联 `etcplus_trans.merchant_trans_id`，累加 `etcplus_trans.merchant_fee_0` | 退款影响待确认 |

| DIFF-002 | Word 示例表缺少“总上传流水数量”和“平台接收流水数量” | 已确认以 Excel 字段取数逻辑为准 |
| DIFF-003 | Excel 中“总成功率”公式与现有报表实现不一致 | 已确认以现有报表实现为准：`已补缴流水数 / 发送短信数量` |
| DIFF-004 | 短信成本说明中同时出现“元”和“分” | 已确认 0.03 元/条；数据库单位仍需代码核对 |

## 7. 风险等级判断

当前建议定为 B 类需求。

理由：

1. 需求主要是运营统计报表，不直接改变交易、扣款、清分或结算结果。
2. 但它涉及金额、收益、成本和成功率口径，错误会影响运营判断。
3. 已确认该报表只作为运营报表，不作为财务对账或结算依据，因此不升级为 A 类。

## 9. 澄清阶段结论

1. 字段口径、成功率公式、短信成本、平台接收流水和收益统计规则已基本确认。
2. 当前已确认现有报表使用 `ep_ap_order.status = 2` 判定已补缴/已缴费，不使用 `payment_status` 字段。
3. 当前剩余待确认项是日期字段来源、助缴业务商户识别条件、分母为 0 时展示口径等代码核对项。
4. 当前可以进入影响分析细化和代码字段核对，但仍不应直接进入开发任务拆分。
