# 复盘沉淀 v1

需求：REQ-DEMO-001 助缴成功率和成本统计报表

本文用于最小试跑，记录这次全流程演练对“AI 辅助编程结构化思想”的启发。

## 1. 本次试跑结论

这次需求适合作为最小试跑，因为它不是纯 CRUD，也不是资金主链路变更。它涉及多表统计、金额单位、状态口径、成功率口径、定时任务、页面展示和导出，足够体现 AI 辅助需求分析的价值。

## 2. 四层体系如何落地

| 层级 | 本需求中的体现 |
| --- | --- |
| 治理层 | 判定为 B 类；金额、状态、成功率必须人工确认；不作为财务结算依据 |
| 流程层 | 从原始材料进入澄清、影响分析、方案设计、任务拆分、开发联调、测试验收、复盘 |
| 资产层 | 使用需求澄清表、影响分析表、任务拆分表、验收清单、复盘模板 |
| 度量层 | 可记录分析耗时、代码定位耗时、返工点、测试遗漏点 |

## 3. 关键经验

| 经验 | 说明 |
| --- | --- |
| 不能只信原始需求字段名 | `payment_status` 在代码中不存在，真实模型是 `status` 和 `pay_status` |
| 不能只信 Excel 公式 | 成功率最终按现有报表实现为准 |
| 已完成需求适合做回放 | 回放能暴露“需求文档、代码实现、测试期望”之间的差异 |
| AI 最有价值的是找冲突 | 比直接生成代码更重要的是发现字段、状态、口径不一致 |
| 人工确认仍然必要 | 成功率、默认日期、是否导出、是否结算依据不能让 AI 自行决定 |

## 4. 本次发现的偏差

| 偏差 | 后续处理建议 |
| --- | --- |
| 文档说默认当天，代码默认昨天 | 如果业务接受默认昨天，更新需求说明；否则另起变更 |
| 文档说商户下拉，代码是商户编号/名称输入 | 如果需要下拉，另起 UI 体验优化任务 |
| 初版非范围说导出未确认，代码已实现导出 | 在最终需求说明中改为已交付能力 |
| 造数脚本期望和现有成功率口径可能不完全一致 | 测试资产需要跟随口径同步维护 |

## 5. 可沉淀为资产的内容

1. B 类运营报表需求澄清模板。
2. 多表统计影响分析模板。
3. 报表类任务拆分模板。
4. 金额/状态/成功率验收清单。
5. 已完成需求回放复盘模板。

## 6. 度量建议

| 指标 | 本次可记录方式 |
| --- | --- |
| 需求分析耗时 | 从读取原始材料到形成澄清文档 |
| 改动点定位耗时 | 从需求字段定位到前端、Controller、Mapper、Job |
| 返工次数 | 例如成功率口径从车牌口径调整为现有报表口径 |
| 测试遗漏数 | 验收后记录未覆盖或后续暴露的问题 |
