# 阶段准入准出规则

## 1. 准入准出原则

每个阶段都要有明确输入、完成标准和下一步动作。

A 类风险需求不得跳过需求澄清、影响分析、方案设计和任务拆分。测试点、验收断言、任务级验证目标和 TDD 适用性在任务拆分阶段定义，开发期 TDD 和替代验证在开发与联调阶段执行，交付前验证在测试与验收阶段闭环。

## 2. 阶段规则

| 阶段 | 准入条件 | 准出条件 |
| --- | --- | --- |
| 原始材料 | 有需求来源或问题描述 | 原始材料已归档，来源和上下文可追溯 |
| 需求澄清 | 原始需求已归档 | 范围、非范围、待确认项已列出；**「澄清确认单」的阻塞项已全部人工拍板并冻结（硬门禁）** |
| 影响分析 | 澄清问题已有初步结论 | 影响模块、接口、数据、风险已列出 |
| 方案设计 | 关键影响面已识别 | 高风险口径有人工确认或挂起说明 |
| 任务拆分 | 方案边界基本明确 | 任务可排期、可分工、可验收，验收断言、任务级验证目标和 TDD 适用性已定义 |
| 开发与联调 | P0 口径、风险和任务边界已确认；**「编码前理解确认」已人工通过（硬门禁，未通过不许编码）** | 代码改造、TDD 或替代验证、代码 Review、联调和问题闭环已有记录 |
| 测试与验收 | 开发与联调记录具备验证条件 | 主链路、异常链路、权限、回归、完成前验证和剩余风险已有结论；**「测试可信度报告」已通过：每条验收标准有测试、红灯证据齐、变异分数达阈值、假测试自检通过（硬门禁）** |
| 复盘沉淀 | 需求完成或阶段结束 | 经验、问题、资产改进已记录 |

## 3. 三个快速确认硬门禁（防"没澄清就编码、假测试蒙混"）

| 门禁 | 位置 | 通过标准 | 人审时间 |
| --- | --- | --- | --- |
| 澄清确认单 | 需求澄清准出 | 阻塞项全部人工拍板并冻结 | ~1 分钟 |
| 编码前理解确认 | 开发准入 | 验收标准→实现思路映射经人工"通过" | ~30 秒 |
| 测试可信度报告 | 测试准出 | AC↔测试映射全覆盖 + 红灯证据 + 变异分数达阈值 + 假测试自检通过 | ~2 分钟 |

详见 `01-流程层/人类快速确认指南.md` 与 `02-资产层/02-模板库/04~06`。
